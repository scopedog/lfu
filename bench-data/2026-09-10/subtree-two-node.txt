Root vs subtree: llapi_scan_mount() restricted to a directory (design-llapi-scan §5.1)
======================================================================================
2026-09-10.  Server 192.168.122.10 (rhel9.7-server-mgs-mds-clone: MGS +
lustre-MDT0000 + 2 OSTs, loop files), client 192.168.122.101
(rhel9.7-client-clone), both VMs on one host over virbr1.  Same machines,
same fixture and same offload path as rpc-two-node.txt.
Fixture: the 2026-09-09 llmount filesystem, 88,230 MDT inodes, mounted with
NOFORMAT=1.  One MDT.

    /mnt/lustre              87,944 regular files, the whole filesystem
    /mnt/lustre/bench        87,894 files under 10 dirs   (99.9%)
    /mnt/lustre/bench/d3     10,000 files, one dir        (11.4%)
    /mnt/lustre/d0               50 files, one dir        (0.06%)
    no hard links (find -links +1: 0)

What changed: llapi_scan_mount() honours the directory it is given.  Root
asks for everything, as before.  Any other directory runs a directory-only
pre-pass building the FID -> (parent, name) map (scan_dirmap_prepass(), the
--paths machinery), then the search pass delivers an object only when its
parent lies beneath the named directory.  The walk up the map is memoised
per directory entry, so the total cost is one walk per directory, not one
per object.  Objects outside are counted as filtered.  Client-side only: the
MDT still streams every object.

Library under test: lustre-scanfid lu-20720-fold + the subtree change,
liblustreapi.so md5 aa07bd58aa83 on both nodes; the committed source is
byte-identical to what was built (checked with md5 local vs server).

Arms, alternated, caches dropped on BOTH nodes before every run:
  stock    lfs find SCOPE -mtime -30 -type f    ~/lustre-release on the
           client, lfs 2.17.52_533_g9ec0025, no LFU in it
  walk     llapi_scan_namespace(SCOPE)  via tests/lab-sub/subfind.c
  offload  llapi_scan_mount(SCOPE)      via the same harness
Both library arms ask lfsp_want = FID|TYPE|MTIME and apply the same
predicate in the callback.

Three things found on the way, and two runs thrown away
--------------------------------------------------------
1. A walk asking for everything is not a baseline.  The first benchmark
   left lfsp_want at 0: the walk arm took 21-22 s cold at the root, where
   stock lfs find over the same tree takes ~9 s, because it paid round trips
   for layouts and xattrs the predicate never reads -- while the offload
   gets them free in the record.  Stopped after two pairs; a ratio against
   that arm would have been inflated.

2. "-type f" alone is a readdir.  The second benchmark narrowed the
   predicate to -type f (-mtime -1 now matches 4 files: the fixture is past
   24 h), and stock lfs find answered the root cold in 0.172 s: the type is
   in the dirent, so there is no per-object request at all.  Stopped after
   one row.  That measures readdir, not the cost this offload removes; and
   it is a finding in its own right for the dispatcher -- a predicate the
   dirent answers is never worth offloading.  -mtime -30 keeps the earlier
   run's cost profile (a stat per file) and matches every file.

3. A predicted bug that did not reproduce.  With lfsp_want = FID|TYPE the
   parent is not asked for, so the subtree test should have judged every
   object parentless and delivered nothing.  Tested against the UNFIXED
   library first: d0 answered 50 and d3 10,000, correct.  The stream backend
   ships the link tail unconditionally and scan_lfu_rec_to_obj() marks it
   valid whatever the mask says.  The guard stays -- a subtree scan now
   asks for PARENT|LINKEA itself -- because the obvious next optimisation,
   telling the MDT not to ship an unwanted tail, would otherwise turn every
   subtree scan into a silent empty answer.  It costs nothing today.

What it says
------------
1. The root reproduces the earlier result: 30.8x stock, 0.291 s against
   rpc-two-node.txt's 0.292 s.  Nothing on the root path moved.

2. A subtree offload costs the same whatever the subtree holds: 0.405-0.412
   s for 87,894 files, for 10,000 and for 50.  It is the root's 0.291 s plus
   the directory-only pre-pass, +0.114-0.121 s, about 40% of a root offload,
   and it makes two sweeps' worth of round trips (42-44 against 21).  This is
   design-llapi-scan §5.1 measured: O(filesystem) read plus O(subtree) output,
   never O(subtree).

3. The restriction still pays for large subtrees: bench/d3, a ninth of the
   filesystem, is 6.2x stock.  It loses badly for small ones: d0 is walked
   in 0.035 s and offloaded in 0.404 s.  Note the offload makes FEWER round
   trips than the walk there (42 vs 57) and still loses 11x -- each of its
   carries a megabyte, and a round-trip count is not the right proxy once
   the subtree is small.

4. The crossover is a fraction of the filesystem, not a file count.  The
   offload's cost scales with every object on the MDT (0.405 s / 88,051 =
   ~4.6 us per object); the walk's with the files beneath the directory
   (102 us per file at the root, 251 us in d3 -- not linear here).  Equal
   when the subtree holds 1.8-4.5% of the filesystem: ~1,600-4,000 files on
   this one.  INTERPOLATED, not measured: no directory in the fixture holds
   that many, and the fixture is not to be grown.  A real network raises the
   walk's per-file cost and so lowers the fraction; it does not remove it.

5. Rule 6 stands.  The decision wants the subtree's share of the filesystem,
   and the client cannot know it without counting -- which is the walk.

Why the walk arm is 2.4x slower than stock at the root -- and not a defect
---------------------------------------------------------------------------
The walk column is llapi_scan_namespace() with its defaults, and it is NOT a
fair walk baseline: quote stock, never walk/offload (73.6x would be wrong).
At d3 and d0 the two agree; at the root and bench the walk takes 21 s to
stock's 9 s.  Three checks, one cold run each:

  not OST glimpses   osc RPCs: 0 for both arms; mdc RPCs 88035 vs 88029
  not statahead      stock with statahead_max=0: 8.938 s, 9.252 s -- no
                     change (restored to 128 afterwards)
  concurrency        same opcode, same count, and each request is FASTER
                     for the walk:

    arm     wall     user   sys     mds_getattr_lock   waits summed   in flight
    stock   8.89 s   1.31   10.00   87944 @ 322 us     28.85 s        ~3.2
    walk   19.39 s   0.09    1.75   87944 @ 207 us     18.57 s        ~1.0

Stock waits 28.85 s on requests inside an 8.89 s wall, with user+sys above
the wall: several at once.  The walk waits 18.57 s inside 19.39 s: one at a
time.  In source, lfs find picks its threads in
calculate_default_thread_count() (lfs.c): min(4 per MDT, half the
CPUs), and never below 4 -- so 4 on this 4-CPU client.  llapi_scan_namespace()'s lfsp_thread_count is "0 or 1:
the caller's own thread" (lustreapi.h).  The harness left it unset.  (That
formula is from this series' tree; the client's stock lfs is 2.17.52, whose
parallelism the measurement shows whatever its formula.)

Consequence for llapi_scan(): a walk branch that calls
llapi_scan_namespace() with its defaults is 2.4x slower than the lfs find a
user already has.  It must carry find's default parallelism.  Not measured
with threads set: the lab was shut down after this.
