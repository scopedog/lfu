The walk with lfsp_thread_count set (design-llapi-scan open question 6)
=======================================================================
2026-09-10.  Follows subtree-two-node.txt, which found llapi_scan_namespace()
2.4x slower than stock lfs find at the root with the same 88k getattrs,
no OST requests and statahead ruled out -- because the scan ran one request
at a time (lfsp_thread_count defaults to the caller's own thread) where lfs
find ran ~3.2 at once.  This sets the thread count and measures again.

Same two VMs (server 192.168.122.10, client 192.168.122.101, 4 vCPUs each),
same 88k fixture remounted with NOFORMAT=1 (lfs df -i: 88,230 used, as
before), same predicate -mtime -30 -type f, same library
(liblustreapi.so md5 aa07bd58aa83 on both nodes).  The harness gained a
thread-count argument and an atomic match counter: above one thread its
callback runs on several workers at once, and a plain ++ would undercount.

What stock lfs find uses, from source (calculate_default_thread_count(),
lfs.c; the client's 2.17.52 tree has the same function):
    threads = min(4 x MDTs, CPUs / 2), then raised to at least 4
On this client, one MDT and 4 CPUs: min(4, 2) = 2, floored to 4.  So stock
runs 4 threads here, and ns4 is the like-for-like arm.  (The MDT count comes
from llapi_get_obd_count(), which the llapi_scan_mount() work found returns
the descriptor array size rather than the MDT count; it cannot change the
answer on this client, where the floor decides.)

Arms, alternated, caches dropped on BOTH nodes before every run
(tests/lab-sub/benchthreads.sh):
  stock   lfs find, its default (4 threads here)
  ns1     llapi_scan_namespace(), lfsp_thread_count = 1 (the default)
  ns4     llapi_scan_namespace(), lfsp_thread_count = 4
  ns8     llapi_scan_namespace(), lfsp_thread_count = 8
  mount   llapi_scan_mount(), for reference

What it says
------------
1. The gap was the default and nothing else.  With lfsp_thread_count = 4,
   stock's own count here, llapi_scan_namespace() matches lfs find: 1.02x at
   the root, 0.97x for bench, both inside the +-3% spreads.  Same request
   count, same opcode, and now the same concurrency: 3.32 in flight against
   3.25.  One thread is 2.37x slower; that is the whole story of
   subtree-two-node.txt's walk column.

2. Threads parallelise ACROSS directories, not within one.  bench/d3 is a
   single directory of 10,000 files, and every arm walks it one request at a
   time -- 0.93-0.95 in flight for stock, 1, 4 and 8 threads alike -- so
   threads buy nothing there (2.39-2.53 s, inside the spread).  The idle
   workers still cost CPU: user+sys 2.6 s at 4 or 8 threads against 0.25 s
   at one, for the same wall.  d0 is too small for threads to matter.

3. Past stock's count, the MDT is the limit.  8 threads put 6.26 requests
   in flight and each slows from 320 us to 539 us, so twice the concurrency
   buys 1.16x (0.88x stock at the root, 0.85x for bench).  That is this
   lab's MDT -- one VM, loop-file targets -- and says nothing about a real
   one; it is not a case for a higher default.

4. The offload's ratios hold against a fair walk.  Against ns4: 30.7x at
   the root, 21.9x for bench, 6.1x for d3, and still 11x slower for d0.
   subtree-two-node.txt quoted stock rather than its walk column, and stock
   and ns4 agree, so none of its conclusions move.  The crossover bracket
   is unchanged: ns4 costs 103 us per file at the root and 249 us in d3,
   against the offload's ~4.6 us per object on the MDT -- 2-5% of the
   filesystem.

5. For llapi_scan(): the walk branch must not inherit the scan's default of
   one thread, and with find's count it loses nothing to lfs find.  The two
   ways to get there are in design open question 6.  Not measured: DNE,
   where find's formula reads llapi_get_obd_count() for the MDT term -- the
   call that answers 64 on one MDT -- so on a client with more than 8 CPUs
   it would pick CPUs/2 rather than 4 per MDT.
