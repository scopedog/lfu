  in-kernel WARM, attrs       390,720 obj/s     388,293 / 386,418
  in-kernel WARM, bare FID    391,255 obj/s     387,691 / 384,265
  in-kernel COLD, attrs       165,763 obj/s     165,174
  userspace COLD             173,671 obj/s     173,283
  userspace WARM -j 1        1,669,216 obj/s   1,681,095

Warm moved by -0.8%. Density is not the cause.

Why it could not have been, from the source: osd_iit_next() (osd_scrub.c:518)
advances with ldiskfs_find_next_bit() over the group's inode bitmap, and
osd_scrub.c:1120 skips any group flagged LDISKFS_BG_INODE_UNINIT outright.
Unused slots are never visited.  ldiskfs also packs allocations, so both arms
held their 2M inodes in ~the same number of groups (67 vs 62) — occupancy
percentage was never the operative variable.

[B7] best remaining candidate — MDT inode size (UNTESTED)
----------------------------------------------------------
A 512-byte inode halves the inode-table bytes the iterator reads per object
and would explain a clean ~2x (832k vs 390k).  This lab formats 1024-byte
inodes (dumpe2fs "Inode size: 1024").

Note the apparent cold agreement is weak evidence against this: lab A's cold
figure (167k) was a scrub-derived estimate, never a direct measurement, so
"cold agrees" does not actually constrain the hypothesis.

Test: reformat with --mkfsoptions="-I 512", recreate 2M, re-run warm.

[B9] ...but it confirms the cold bandwidth model
-------------------------------------------------
Halving bytes-per-object doubled the COLD rate at constant device bandwidth:

  -I 1024 : 173,283 obj/s x 1024 B = 177.5 MB/s
  -I  512 : 350,664 obj/s x  512 B = 179.5 MB/s

Same disk, within 1%.  This is the direct confirmation of

        cold obj/s  ~=  metadata read bandwidth / bytes per object

which until now was arithmetic on a single point.  Warm, by contrast, is
insensitive to bytes (+2.6%) -- cold is bytes, warm is CPU.

Practical consequence: MDT inode size is a real lever on full-scan time.
Caveat: these are createmany -m (mknod) objects with no layout; a striped
file's LOV + linkea at 512 B would likely spill to an external EA block and
give the gain back.
