########## the MDT_INDEX drop, measured (mdtidx_probe.c)

The open comment on liblustreapi_scan.c:317 asks whether an object the caller
cannot open drops out of a scan.  It does, when the demand mask names
LLAPI_SCAN_MDT_INDEX.  Same tree, two scans, counting delivered records:

  probe2, every file readable, as non-root
    TYPE only         4 objects (rc 0)
    TYPE | MDT_INDEX  4 objects (rc 0)      no drop

  probe, one root-owned mode-000 file, as non-root
    TYPE only         6 objects (rc 0)
    TYPE | MDT_INDEX  5 objects (rc 0)      ONE DROPPED, rc still 0

  the same tree as root
    TYPE only         6 objects (rc 0)
    TYPE | MDT_INDEX  6 objects (rc 0)      no drop

The object is not reported and no error reaches the caller: scan_rec_gather()
returns -EACCES from the open, llapi_scan_cb_init() takes goto out, and the
scan ends 0.  PROJID and HSM no longer behave this way -- they test the call
and leave the bit clear -- so 68094's message, "An object the caller cannot
open leaves the bit clear rather than dropping out of the scan", is true for
two of the three bits and false for MDT_INDEX.

A first attempt at this probe measured "all 6 objects dropped" and was wrong:
conf-sanity 165's cleanup had torn down the client, /mnt/lfufs was xfs on the
boot disk, and every Lustre ioctl answered ENOTTY as it should.  stat -f -c %T
says lustre before the numbers above.
