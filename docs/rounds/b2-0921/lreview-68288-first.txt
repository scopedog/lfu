(4) lustre/utils/liblustreapi_scan_device.c (line 503)
    (minor) `struct filter_fid` is `__attribute__((packed))`, so taking the address of `ff_parent` draws -Waddress-of-packed-member, which gcc has on by default:

        warning: taking address of packed member of 'struct filter_fid'
                 may result in an unaligned pointer value

    ll_decode_filter_fid.c sidesteps it by reading `ff->ff_parent.f_seq` and `.f_oid` directly rather than keeping a `struct lu_fid *`. Copying the two fields into a local lu_fid in each arm would keep the shared tail below and lose the warning.

(5) lustre/utils/liblustreapi_pfind.c (line 3569)
    (minor) -printf with either option is refused here, but fp_paths together with fp_fid2path_mnt is only refused by lfs_find_device() in lfs.c -- a library caller that sets both reaches the scan. On an MDT the map wins and fc_mnt_path is non-NULL, so the answers come back prefixed with the mount point, which is exactly what fp_paths documents it will not do; on an OST the pre-pass's -ENOTDIR fires even though fp_fid2path_mnt could have named the objects. Since the two are already mutually exclusive on the command line, should the same check live here so llapi_find_device(3) is self-consistent?

(6) lustre/utils/liblustreapi_pfind.c (line 4250)
    (minor) The --paths arm was moved off `dm_used != 0` onto "was --paths asked for", but --fid2path still keys off what the pre-pass found rather than whether it ran. An MDT whose files all sit directly in the filesystem root ends the pre-pass with dm_used == 0 (ROOT, .lustre, lost+found get no trusted.link, so scan_dirmap_cb() never inserts them), and --fid2path then falls through to llapi_scan_rec_path() -- one llapi_fid2path_at() per object, against the MDT being scanned. That is the route the surrounding comments say must not be taken for a target that may be out of service, and it is reachable under DNE with the scanned MDT stopped and the mount served by another. Would tracking "the pre-pass ran" cover both cases the same way?

(7) lustre/utils/lfs.c (line 6446)
    (suggestion) This sweep already skips the targets --ost/--mdt cannot name. --paths is the same shape of question: it is an MDT-only option, so on a combined MDS/OSS `lfs find --local --paths` reports a -ENOTDIR failure for every OST and exits non-zero even though every MDT answered. Skipping OSTs here when fp_paths is set would make the sweep behave like the --mdt one.
