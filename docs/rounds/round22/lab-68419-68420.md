## Two things the lab corrected, both in our own record

### 1. `797f62e9`'s stated repro is wrong — the CLI cannot reach that message

The review said *"`lfs find --since-cookie job.ck --resolve /mnt/lustre` lands
here and is told that `--since already reads the object`"*, and round 21's
triage repeated it. **It does not.** `lfs_find_parse()` carries a guard with
the **identical condition** — `fp_resolve && fp_changelog_mdt == NULL` — and
refuses first with its own message:

    lfs: --resolve fills in what a changelog lacks; it needs --changelog

`lfind` shares that parser, so neither command can reach the library's line.
The control run printed the parser's message plus the usage block, which is
what exposed it.

**The finding is still real, and the fix still right** — just for a different
caller. `llapi_find_since()` is public (`lustreapi.h:1011`), and a program
calling it directly with `fp_resolve` and no changelog MDT reaches the library
guard. Proved with `resolve_guard.c`, which on the control build prints
exactly the message the review quoted:

    --resolve fills what a changelog lacks; --since already reads the object
    llapi_find_since rc=-22

So the arm tests the reachable path, and the Gerrit reply must say the repro
was the command line, not claim the scenario as given.

### 2. `d1c134a5`'s ENAMETOOLONG branch needs a deep path, not a long name

My first arm used a single 4090-character component and **failed on the fixed
build** — which looked like the fix not working. It is not: `find_cookie_read()`
runs before `find_cookie_check()`, and its `fopen()` refuses a component over
`NAME_MAX` (255), so a long *name* never reaches the new message.

The reachable window is a path of **4092–4095** whose components all fit —
long enough that `"%s.new"` overflows `probe[PATH_MAX]`, short enough that
`fopen()` reaches `ENOENT` and treats it as the first run. Measured:

| cookie path length | outcome |
|---|---|
| 4090 | accepted (the run proceeds) |
| **4092–4094** | **`the cookie '…' is too long to write beside`** |
| ≥4096 | `cannot read '…': File name too long` — `fopen()` first |

The arm builds sixteen 250-character directories to get there. An arm that
tests an unreachable input reports a false failure, which is
[[lfu-lab-fixture-discipline]] in a new place.

## And a trap in my own harness, not in the tree

`resolve_guard.c` first segfaulted inside `llapi_error()`, which looked like a
defect in a public entry point. It was a **header mismatch**: the tree keeps
`lustreapi.h` at `include/lustre/`, not `lustre/include/lustre/`, so my `-I`
pointed at nothing and gcc used `/usr/include/lustre/lustreapi.h` — **79110
bytes, dated Sep 3, against the tree's 82084**. Different `struct find_param`
layout, so `fp_since_cookie` read as garbage.

Two lessons: the installed header on that VM is stale, so anything compiled
against it has an ABI mismatch with the installed library; and a segfault
reached through a wrong include path says nothing about the code.
