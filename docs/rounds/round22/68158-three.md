# 68158 `46c9be5f`, `25ba086d`, `8516da85` — the shared parser's contract

2026-09-08, tenth through twelfth of the seventeen. One declined on evidence,
two fixed — and the middle one turned out to be a **reachable, user-visible
bug**, not the contract note the comment offered it as.

## `46c9be5f` — declined, and the reason is measurable

The suggestion: move `fp_min_depth > fp_max_depth` out of `lfs_find()` and
into `lfs_find_parse()`, since it is a consistency check between two parsed
predicates and `lfind` will otherwise have to repeat it.

**It will not.** `lfind` calls `llapi_find_device()` and nothing else
(`lfind.c:418`) — it never walks — so `--mindepth` and `--maxdepth` are
refused outright before any range check could matter:

    $ lfind --device /tmp/lustre-mdt1 --mindepth 3 --maxdepth 1
    lfind: --maxdepth and --mindepth describes a walk, which a target scan is not

Moving the check would make that answer **worse**: the parse runs first, so
`lfind` would complain that 3 > 1 for two options it does not support at all,
and the message that says so would never print. The predicted second copy
does not exist and should not.

## `25ba086d` — a real bug, reproduced

`execute_line()` in `libcfs/libcfs/util/parser.c:384` sets `optind = 0` before
calling a command, which is the interactive `lfs` shell. `prev_optind` seeded
from that 0, so `pathstart` came back 0 and the search included `argv[0]`:

    $ printf 'find /tmp -maxdepth 0\nquit\n' | lfs
    lfs: failed for 'find': No such file or directory
    /tmp

It searched the string `find`. **Verbatim upstream** —
`5afbab284e:lfs.c:7256` has `int prev_optind = optind;` — so this is not
something the move broke. But our patch *documents* a contract, and that
contract is untrue of a caller in the tree, which is what makes it ours to
either fix or qualify.

Fixed with the comment's own suggestion, `optind ? optind : 1`, which is not
a guess: glibc reads `optind == 0` as "reinitialise" and scans from `argv[1]`
regardless, so 1 is where the parse will actually start. After:

    $ printf 'find /tmp -maxdepth 0\nquit\n' | lfs
    /tmp

Checked that nothing else moved: the argv path unchanged, `-maxdepth 1` still
652 lines against `-maxdepth 0`'s 1, `-mtime +1y` still parses, two paths
work interactively, and `lfind` still runs.

## `8516da85` — the input half of the contract

`lfs_find_parse()` reads four fields it does not set: `fp_max_depth`,
`fp_min_depth`, `fp_quiet`, `fp_time_margin`. `set_time()` only widens the
margin while `fp_time_margin` is still `FP_DEFAULT_TIME_MARGIN`, and
`llapi_find()` stops descending at `fp_depth == fp_max_depth`, so a caller
handing over a zeroed structure walks the top directory only.

Added `lfs_find_parse_init()`, paired with the `fini()` that was already
owed, and switched both front ends to it. That is exactly the drift the patch
exists to head off — and `lfind`'s copy was **already one field short**,
naming three of the four and leaving `fp_min_depth` to the designated
initialiser.

## The rebase: one change, two commits

`lfind.c` does not exist at 68158, so this could not be one fixup. Split by
file — `lfs_find_parse.c/.h` and `lfs.c` into 68158, `lfind.c` into 68160 —
and the `lfind.c` half then conflicted **twice** with the `sp_` → `lfsp_`
rename, once in each direction, the same shape as `0aaa4e59`'s. Verified
after: 68158 touches no `lfind.c`, 68160 touches only it, tree hash unchanged
through both rewordings.
