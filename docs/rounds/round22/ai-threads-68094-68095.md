## 68094 — `LU-20603 llapi: namespace scanner API`

### `6813c461` — `sp_want = STATX_INO` returned zero, silently

The one with a wrong answer. `lustreapi.h` promises `LLAPI_SCAN_STATX_MASK`
is *"the whole of that half, whether this API has a name for the bit or
not"*, so `STATX_INO` is a legal ask. But `scan_rec_gather()` gates on
`LLAPI_SCAN_MDT_MASK`, and `STATX_INO` was in **neither** that mask nor
`LLAPI_SCAN_DIRENT_MASK` — so the scan returned before any fetch and the
field arrived zero with its bit clear.

`STATX_TYPE`'s absence from the MDT mask is a decision (it comes from the
dirent); `STATX_INO`'s was an oversight, and nothing fills it but the ioctl.

**Measured on the lab, three arms, before and after:**

| `sp_want` | before | after |
|---|---|---|
| `STATX_INO` alone | **`stx_ino=0`, `stx_mask&INO=0`** | `stx_ino=144115188193296385`, bit set |
| `STATX_INO\|STATX_SIZE` | correct | unchanged |
| `0` (everything) | correct | unchanged |

The middle arm is what makes it a defect rather than a limitation: the same
field, asked for two ways, answered two ways. Fixed by naming `STATX_INO` in
`LLAPI_SCAN_MDT_MASK`.

### `0397b439` — a shared helper threw away a caller's FID

`convert_lmd_statx()` ended with a `memset` of `lmd_fid`, and its comment
said *"neither caller has a FID to give"*. It has **three** callers, and the
third — `cb_find_init()` under `gather_all`, i.e. `lfs find -printf` — runs
after the V2 ioctl has already put a real FID there.

No visible effect today: nothing reads `lmd_fid` on that path. But the patch
after this one moves `lfs find` onto the record, where `sr_fid` is filled
from it (`liblustreapi_scan.c:142`), and `pfind.c:3709` fills it the other
way. The clear now lives at the two sites that genuinely have no FID —
`convert_lmdbuf_v1v2()` and the `lstat()` fallback in `get_lmd_info_fd()` —
and `scan_rec_gather()`'s comment names the new location.

### `7611a1a0` — `LLAPI_MSG_DEBUG` quiets nothing

Verified in full, and the reviewer is right on both counts:

- `llapi_msg_level` starts at `LLAPI_MSG_MAX` (7); the filter is
  `if ((level & LLAPI_MSG_MASK) > llapi_msg_level) return;`, and DEBUG is 6,
  so it still prints. Neither `lfs` nor `lfind` calls
  `llapi_msg_set_level()`. `error_callback_default()` never consults the
  level at all — so what actually changed in the diff is the dropped
  `"warning: "` prefix, not the volume.
- The comment claimed *"every caller reports the failure itself"*.
  `scan_rec_gather()` deliberately does not; it leaves `LLAPI_SCAN_PROJID`
  clear.

Comment and commit message both corrected to say what the level does buy —
a caller able to silence it — rather than a flood it does not prevent.
Behaviour left alone: lowering the library's default level is a much larger
call than this patch.

### `d191189e` — a comment orphaned from its function

The must-be-zero paragraph describes `scan_param_padding_ok()` and had come
to sit above `scan_param_whole()`, which has a comment of its own. Moved
back.

## 68095 — `LU-20605 llapi: build find on the scan record`

### `440a87f7` — an object with no project id matched neither `--projid 0` nor `! --projid 0`

Real, and reproduced. The `ENOTTY` arm substitutes `DEFAULT_PROJID` (0) for
an object that has **no** project id, then falls into

    bool matches = projid == param->fp_projid;
    if (matches == param->fp_exclude_projid)
            goto decided;

For N=0 the stand-in equals the number asked for, so the negated form
rejects too — contradicting the arm's own comment, which says
`! --projid N` *"can be answered: whatever the object's is, it is not N"*.

**On the lab**, a directory with two regular files and a symlink (the symlink
is the `ENOTTY` case, via `LL_IOC_PROJECT` on a parent that lacks it):

| | before | after |
|---|---|---|
| `--projid 0` | `npj`, `a`, `b` | unchanged |
| `! --projid 0` | **nothing** | **`npj/l`** |
| `--projid 5` | nothing | unchanged |
| `! --projid 5` | all four | unchanged |

Before, the symlink was in neither answer; now it is in exactly one, and the
two spellings partition the objects. Fixed by skipping the comparison for an
object that has no project id rather than substituting a value for it —
`-printf` still prints `DEFAULT_PROJID`, which is what the stand-in is for.

### `36c4ca49` — two hunks the message never described

True: the `get_projid()` and `cb_find_init()` project-id hunks are both
user-visible and were not among the four listed deltas. Added, together with
what `440a87f7`'s fix changes.

### `937bc492` — the `-name` trailing-slash delta, measured

Real as a delta. `-name` now tests `rec->sr_name`, which `scan_rec_dirent()`
sets to the **whole path** when the last `/` is a trailing one; the old code
took everything after the last `/`, which is `""` for `/mnt/lustre/`.

The reviewer said neither value is `find(1)`'s basename. **Measured, and
that is exactly right** — my first check used one pattern and looked like
agreement, which it is not:

| pattern, start point `/mnt/lustre/` | GNU find | new | old |
|---|---|---|---|
| `lustre` | matches | no | no |
| `*lustre*` | matches | matches | no |
| `*/` | no | **matches** | no |

So all three differ. `find(1)` strips the trailing slash and tests the
basename, which is the behaviour worth having — but `sr_name`'s value for a
trailing-slash start point is a record-contract question, not something to
settle inside this patch. **Listed in the commit message as a delta, with
the `find(1)` comparison; behaviour unchanged.** Worth its own decision.
