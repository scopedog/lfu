(3) lustre/utils/liblustreapi_scan_device.c (line 304)
    (minor) Does the clearing reach as far as the comment above claims? room works out to (4096 - sizeof(struct lmv_user_md)) / 24, so 168 entries, while lum_stripe_count is reported as the directory's real count and LMV_MAX_STRIPE_COUNT is 2000 (overstriping can put several stripes on each MDT).

    For a directory past 168 stripes the memset stops at room, so the consumer the clearing exists for -- one sizing lum_objects[] by lum_stripe_count, as lmv_dump_user_lmm() does -- still reads off the end of sw_lmv.sl_buf, now into the rest of struct scan_worker.

    The header already tells consumers to measure by lfsr_lmvsize, so this is about the comment promising a guarantee the memset cannot give at legal stripe counts.

(4) lustre/utils/libscan_ldiskfs.c (line 383)

    Not a bug in practice: enable_default_ext4_features() always appends huge_file when e2fsprogs supports it, so a mkfs.lustre-formatted target has it. Just worth the helper if this is touched again.
