## Findings

### 1. `lustre/utils/lfs.c` (line 6717)

(suggestion) A sweep skips the targets of the other type for --ost and --mdt. Layout options get different treatment: llapi_find_device() returns ENOTSUP for every OST, and the sweep's exit status then says it failed.

On a node that serves both an MDT and an OST, `lfs find --local --pool flash` (or --stripe-count, --layout, ...) answers in full from the MDT, since no OST data object can carry a layout. It still prints "the layout options need an MDT" for each OST and exits non-zero, so a script reads a complete answer as a partial one.

Could a sweep skip OSTs when the search asks about the layout, as it does for --mdt? find_asks_layout() is static in the library, so this may need a small exported helper or a flag. If the current behaviour is deliberate, ignore this.

### 2. `include/lustre/lustreapi.h` (line 502)

(suggestion) This isn't a bug, but these three pointers and the fp_local_targets/fp_scan_internal bits become part of the public struct find_param, while the comment says the library ignores them.

An llapi user who sets fp_device and calls llapi_find() gets an ordinary namespace walk, with nothing to say the field was not used. Once these fields are in the installed header, they are hard to remove later.

Would a small lfs-private struct beside find_param, filled by lfs_find_parse(), keep the public API free of options that only lfs reads?
