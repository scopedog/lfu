## Findings

### 1. `/COMMIT_MSG` (line 12)

(minor) "a cookie is exact on every MDT" (and "The only anchor that is exact on every MDT" in lustreapi.h) claims more than lfs-find.1 does. The man page says a record can be lost to a race in the MDT, and the code shows how:

    mdd changelog write: cr_index = ++mc_index; up_write(&lgh_lock); dt_record_write(); set bitmap bit
    llog_process_thread(): llog_is_index_skipable() skips a bit not yet set

So a run that reaches the live tail can see N+1 while N is still in flight, anchor at N+1, and the next run starts past N with nothing said. If the patch is refreshed, maybe "exact as long as the log is not purged past it", or hold the anchor back off the last moments of the stream (re-reporting a tail is the failure the rest of the patch prefers to a loss).

### 2. `lustre/utils/liblustreapi_pfind.c` (line 4955)

(suggestion) The root compared here is realpath() on this client, so it carries the mount point. The same subtree of the same filesystem through another mount is refused:

    lfs find /mnt/lustre/data  --since-cookie ck   # writes "under /mnt/lustre/data"
    lfs find /mnt/lustre2/data --since-cookie ck   # -EINVAL, "not under '/mnt/lustre2/data'"

That is a cron job moved to a client that mounts at /lustre, or $MOUNT2, and the only way forward is removing the cookie, which rescans and reprints every log. The anchors belong to the filesystem, so would recording the root relative to mnt_path (rootbuf + strlen(mnt_path)) bind the cookie to the search without binding it to one client's mount point?
