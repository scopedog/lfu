## Overall assessment

Some concerns, see inline comments. The lfu_noverify module parameter looks like experiment scaffolding that changes OI scrub behavior and is not part of the described change; it should be dropped or split out before this lands. The new DOIF_ATTR / DOIF_PARALLEL paths also have no test coverage in this patch.

## Findings

### 1. `lustre/osd-ldiskfs/osd_scrub.c` (line 322)

(defect) The commit message never mentions this module parameter. It is described as an "LFU experiment" and turns off OI verification in the production scrub.

When it is set, the jump to `skip` happens before `oii` is assigned. So when the scrub is working on an item from `os_inconsistent_items` (`os_in_prior`), that item is neither freed nor moved to stale. It stays at the head of the list:

    osd_scrub_next() -> picks the same oii again (returns 0)
    osd_scrub_exec() -> osd_scrub_check_update() -> skip, rc = 0
    -> os_in_prior = 0, return 0 -> loop

That looks like a CPU-bound loop in the scrub thread with no sleep in it. Meanwhile, the lookup that queued the item through osd_scrub_oi_insert() keeps getting -EINPROGRESS. Even without inconsistent items, a full scrub (e.g. SF_RECREATED after a backup/restore) would record completion and clear the flags without rebuilding a single OI mapping.

The parameter is still present at the tip of the series and nothing in the series reads it. Can it be removed from this patch? If it is needed for benchmarking, a CFS_FAIL_CHECK() might be a safer way to do it. Separately, the definition sits between two groups of #includes, and the name doesn't carry the osd_ldiskfs module prefix.

### 2. `lustre/osd-ldiskfs/osd_scrub.c` (line 732)

This gives a much smaller attribute set than the ZFS side and than dt_attr_get() on this OSD. Fields like la_flags (immutable/append/encrypt), LA_PROJID, LA_BTIME, LA_BLKSIZE, LA_TYPE and LA_RDEV are all left out, while osd-zfs's osd_otable_it_attr() fills most of them. The commit message says "a consumer asks the same question of either", but the answers differ in la_valid. A consumer that filters on project ID or flags would quietly fall back to a re-read on ldiskfs only.

osd_inode_getattr() in osd_handler.c already does exactly this from an in-hand inode. Could it be exported and reused here? That would keep DOIF_ATTR results identical to dt_attr_get().

### 3. `lustre/osd-zfs/osd_scrub.c` (line 1686)

Is this rationale accurate? In osd_attr_get(), a directory's la_size is `512 * blocks` from sa_object_size(). zap_count() only fills la_dirent_count, and it reads the ZAP header count rather than walking the ZAP.

As written, this helper returns the raw SA size (osa->size) for directories, which differs from what dt_attr_get() returns. `blocks` is already computed below, so it would cost nothing to match it:

    if (S_ISDIR(la->la_mode))
        la->la_size = 512 * blocks;

That would also let the "must still fall back to dt_attr_get() for directories" caveat go away.

### 4. `lustre/osd-ldiskfs/osd_internal.h` (line 224)

(minor) This adds 64 * sizeof(struct lu_attr) (about 6.5KB) to every osd_otable_it. That includes the LFSCK/scrub iterator, which never sets DOIF_ATTR, and DOIF_PARALLEL instances, which only use slot 0 of both arrays. The structure grows to roughly 9KB, allocated with a plain OBD_ALLOC_PTR(). If the patch is refreshed, consider allocating the attr array only when ooi_want_attr is set, or giving private iterators a single-slot record.

### 5. `lustre/include/dt_object.h` (line 1866)

(style) This isn't a bug, but "(LFU)" appears in comments throughout this patch and nothing in the tree at this point defines it. If the patch is refreshed, consider either spelling out what the tag refers to once (here would be the natural place) or dropping it from the comments.

### 6. `/COMMIT_MSG` (line 27)

`Test-Parameters: ignore` skips testing, but this patch changes the shared OI scrub / LFSCK otable iterator paths: osd_scrub_check_update(), the preload path, rec(), load() and the ZFS next() locking. Should it be dropped, or replaced with a run of sanity-scrub and sanity-lfsck on both ldiskfs and zfs?
