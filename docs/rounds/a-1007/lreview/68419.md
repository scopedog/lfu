## Findings

### 1. `Documentation/man1/lfs-find.1` (line 890)

(minor) Outside the searched tree is not quite enough. A cookie kept anywhere on the same Lustre filesystem still writes that filesystem's changelog on every run:

    find_cookie_check(): create + unlink of <cookie>.<pid>.<n>.new   (the probe)
    find_cookie_write(): create of the temporary, rename over the old cookie

The probe and the replaced cookie are both gone by the next run. find_since_cand_cb() gets ENOENT from llapi_scan_fid() for each one and counts it in fss_gone before any subtree test. So every run under --since-cookie prints "2 of N changed objects no longer exist and are not in the answer", even when nothing else changed, and a cron job mails it every time. Under --changelog, both objects are also printed as matches.

If the patch is refreshed, maybe say to keep FILE off the filesystem being searched, or at least mention the warning.

### 2. `lustre/utils/liblustreapi_pfind.c` (line 6562)

(suggestion) The cookie is fsync()ed before the rename and its directory after, but the matches are not. With

    lfs find /mnt/lustre --since-cookie ck > /var/tmp/out

a host crash soon after the run can leave the cookie durably advanced while out never reached disk. Those matches are then lost for good, which is worse than the rescan the cookie fsync() guards against.

Would fsync(fileno(stdout)) here be worth it when stdout is a regular file? fstat() and S_ISREG() would tell, and EINVAL from a pipe or tty can be ignored.
