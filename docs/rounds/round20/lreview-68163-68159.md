## 68163 — LU-20613 llapi: ZFS backend for llapi_scan_device

**(1) `llapi_scan_device.3:395` — `-ENOENT` is no longer ZFS-only.**
`scan_device_exists()` stats any `@device` beginning with `/` and returns the
raw errno before a backend is chosen, so a mistyped ldiskfs path answers
`-ENOENT` on a node with no ZFS at all. The same call can hand back
`-ENOTDIR`, `-ELOOP`, `-EACCES` and `-ENAMETOOLONG`, and the page describes
`-ENAMETOOLONG` as a ZFS-dataset condition too. *Doc fix.*

**(2) `libscan_zfs.c:72` — the magic 48.**

    #define SCAN_CHUNKS_MAX		((1ULL << 48) / SCAN_CHUNK_OBJS)

`<sys/dnode.h>` is already included at line 39 and spells this
`DN_MAX_OBJECT` (`DN_MAX_OBJECT_SHIFT` 48). Verified present. The comment
also says the id space has no cheap upper bound, which overstates it —
`1ULL << 48` *is* the bound. *One-line fix plus the comment.*

**(3) `liblustreapi_scan_device.c:913` — `-EBUSY` asserts the wrong cause.**
Every `-EBUSY` from the ZFS backend is reported as "its pool is ACTIVE", but
`scan_zfs_open()` has a second source: `dmu_objset_own()` →
`dsl_dataset_tryown()` returns EBUSY when the dataset already has an owner,
which is what a second `llapi_scan_device()` on the same dataset in the same
process hits — the nesting `libscan_zfs.c`'s own `scan_zfs_users` comment
anticipates. The pool is then exported and the advice to export it is wrong.
*Name the dataset, or distinguish the two.*

## 68159 — LU-20611 llapi: run find over a device scan

**(4) `liblustreapi_pfind.c:3506` — undecided counted before the other
predicates run.** `find_device_prefilter()` returns 2 for "no name anywhere"
*before* `find_prefilter()` gets to run, so over an OST target — where no
record has a linkea — `-name X -type d` counts every data object as
undecided even though `-type d` rejects all of them outright:

    find_device_prefilter() -> return 2
    find_device_cb()        -> st->fds_undecided++

`llapi_find_device()` then warns that N objects could not be decided for a
search whose answer is in fact complete. Every other undecided point sits
*after* the checks that precede it — the `fp_check_projid` one runs after
uid/gid/type/layout — so this one is the odd case out.

Fix shape: ask the other predicates first, with `fp_pattern` temporarily
NULL, and return 2 only if none of them rejected. **Safe to mutate `param`
here**: `llapi_find_device()` sets `spl.sp_thread_count = 1` on purpose,
because `param->fp_lmd` is one buffer for the whole search, and says so at
`liblustreapi_pfind.c:5477`. (Worth keeping in mind: `sd_cb` is otherwise
called concurrently — *"first stopper wins: several workers can decide at
once"* — so this single-thread pin is load-bearing, not incidental.)

**(5) `liblustreapi_pfind.c:3117` — a zero-initialised `find_param` is
refused.** `fp_max_depth` 0 is not `(unsigned int)-1`, so the shape a caller
reaches for first fails, and the new man page's EXAMPLES has to set the field
before the call with a NOTES paragraph explaining why. A target scan has no
hierarchy to describe. *Treating 0 and `(unsigned int)-1` alike would beat
documenting the trap* — but it is an API decision, not a defect.

**(6) `llapi_find_device.3:43` — a sentence about a state no record
reaches.** *"An object with neither is counted and reported at the end, not
printed."* `scan_rec_obj()` sets `LLAPI_SCAN_INO` unconditionally
(`liblustreapi_scan_device.c:512`), so the `obj:` form always applies where
the FID one does not — verified. And if it could happen, nothing would count
it: `find_decide()` falls off the end of the print chain without touching
`fc_undecided` and returns 1 as though it had printed. *Delete or correct the
sentence.*

## Fixed 2026-09-03 — five of the six

Folded into the commits that own each site, by amending mid-series: (1)(2)(3)
into `LU-20613 llapi: ZFS backend for llapi_scan_device` and (4)(6) into
`LU-20611 llapi: run find over a device scan`. (5), the `fp_max_depth` API
question, is left for the user to decide.

**(4) came out simpler than the review suggested.** The reviewer proposed
running `find_prefilter()` with the name predicate suppressed. It needs no
suppression: `find_prefilter()` already guards `rec->sr_name != NULL` and
skips `-name` for a nameless record, so calling it plainly answers exactly
the *other* predicates.

    if (param->fp_pattern != NULL && nr == 0 && rec->sr_name == NULL) {
    	int rc = find_prefilter(rec, param, checked_type);

    	return rc != 0 ? rc : 2;
    }

That avoids mutating `param` — which would have been safe here, since
`llapi_find_device()` pins `sp_thread_count = 1`, but only by leaning on that
pin. Reviewed for side effects: `find_prefilter()` writes only
`*checked_type` and returns 0 or 1; the caller reads `checked_type` only when
the result is 0, which this branch never returns.

**(2) is value-identical.** `DN_MAX_OBJECT` is `(1ULL << DN_MAX_OBJECT_SHIFT)`
with the shift 48, checked in the installed `sys/dnode.h` — the same number,
now named.

**(3) touches the message and the man page.** The ZFS `-EBUSY` text is now
*"in use: pool imported, or dataset held"*, and `llapi_scan_device.3` spells
out both sources and says that exporting is not the answer to the second.

## One more found while verifying, and fixed

`groff -ww -z` on the pages this series touches flagged
`llapi_scan_device.3:556`: the EXAMPLES fragment escapes its newline with a
single backslash, which troff reads as a register reference. The page
rendered

    printf("%llu files; %llu seen, %llu skipped0,

with the escape and the closing quote swallowed. **This is the same bug
68288 already fixed in `llapi_scan_rec_path.3`** — one instance was missed.
Fixed in `LU-20606 llapi: scan an ldiskfs target directly`, which owns the
page; it now renders `\n` and the page is warning-free.
