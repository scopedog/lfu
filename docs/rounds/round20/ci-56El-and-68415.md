## `sanity test_56El` fails in CI everywhere, and I cannot reproduce it

Round 19's CI reported on 2026-09-03 evening.  The one new signal in it is
`sanity 56El`, which the janitor calls a **new failure unique to this patch**:

| change | ldiskfs+DNE | zfs |
|---|---|---|
| 68095 | fail | fail |
| 68163, 68417, 68418, 68419, 68420 | fail | fail |
| 68094 (below the test) | pass | pass |

The test is ours -- `96d3aa00fe LU-20605 llapi: build find on the scan
record` added it -- so this is our regression to answer for, and it sits at
the bottom of everything above 68095.

The failing line is the first assertion, not the second:

    $LFS find $dir -printf '%LF %Lc %p\n' > /dev/null 2> $errf ||
            error "lfs find -printf failed on $dir"

so `lfs find` **exits non-zero**; it is not the stderr half.  The plain
`lfs find $dir -type f` above it passes and counts 3, so the walk itself
crosses into the tmpfs subtree correctly.  Only the `-printf` run fails,
and `-printf` is the one thing that sets `gather_all`.

### What it is not

Reproduced against `~/lustre-r18` (the round-18 series, 2.17.57) on the
local lab, both configurations:

| config | result |
|---|---|
| ldiskfs, MDSCOUNT=1, OSTCOUNT=2 | **PASS** |
| ldiskfs, MDSCOUNT=2, OSTCOUNT=2 (`striped dir -i0 -c2`) | **PASS** |

So DNE is not the trigger, and neither is striping: the CI ldiskfs arm is
`+DNE` and striped, the CI zfs arm is neither, and both fail.

Read against the tree, the paths an off-Lustre object takes are all
already handled: `llapi_scan_get_lmv()` lets `ENOTTY` and `ENODATA`
through, `get_lmd_info_fd()` falls back to `lstat()` on `ENOTTY` and
returns 0, `scan_rec_gather()` swallows the MDT-index failure, and the
`%LF` and `%Lc` arms of `printf_format_lustre()` test for it.  None of
those explains a non-zero exit, and none of them differs by backend.

What is left is the environment: CI is **rocky8.10 (kernel 4.18)** with
the client on a separate node; the lab is rhel9.7 (5.14), single node.

### The test threw away its own evidence

`$errf` holds `lfs find`'s stderr, and on the failing branch the test
called `error` without printing it -- so the CI log carries the failure
and no errno, which is why none of the above could be settled from it.
Fixed in `LU-20605`:

    $LFS find $dir -printf '%LF %Lc %p\n' > /dev/null 2> $errf || {
            cat $errf
            error "lfs find -printf failed on $dir"
    }

That is not a fix for the failure.  It is what makes the next round's
log say which call failed and with what, which is the thing this round
could not get.  Still passes on the lab, both configurations.

**Open, and the first thing to pick up.**

### `99c2228d`'s second half was still live, and is fixed now

The minimum was extended through `sc_mdtname`, but the check on it stayed
where it was -- **above** the `sc_size` validation:

    if (sc == NULL || cb == NULL || sc->sc_mdtname == NULL)
            return -EINVAL;
    if (sc->sc_size < LLAPI_SCAN_CL_PARAM_MIN_SIZE || ...

`sc_mdtname` is the last field inside the minimum, so a caller whose
struct stops short of it has that dereference read **past the end of its
own allocation** -- and the size check that would have rejected it runs
one line too late.  The file already states the rule this breaks ("Only
now, and off the copy") for `sc_user` and `sc_mnt`.  Moved below the
memcpy and read off the bounded copy, like its siblings.

`checkpatch`: 0 errors, 0 warnings.  Compiles under `-Werror`.
