## `f98a7d41` — the new one that matters: clearing after a failed read

The changelog reader's exit had three shapes and treated two of them
alike:

| exit | `rc` | flush | clear |
|---|---|---|---|
| end of log | 1 → 0 | yes | yes |
| consumer stopped, or `sc_endrec` reached | 0 | skipped / yes | yes |
| **the read itself failed** | **< 0** | yes | **yes** |

`sl_stop_rc` stays 0 on a read failure, so the run flushed everything
held, **cleared through it**, and then returned the error. Clearing is
irreversible and purges the registered user's whole backlog, so a
consumer that reads a negative return as "this run produced nothing"
and retries from its old checkpoint finds those records gone.

This is the same question the `--since-cookie` anchor answers, and
answers the other way: 68419 deliberately holds the anchor back when a
run dropped matches, so the rerun that ought to find them does not skip
them for good. I strengthened that rule myself earlier tonight, folding
`fss_scan_rc` in *before* the rewrite. The clear should follow it.

    if (rc >= 0)
            scan_cl_clear(sl, true);

The flush still runs either way — delivering what is held costs the
caller nothing, where clearing it cannot be undone. End-of-log is
already folded into `rc == 0` above, and a break out of the loop leaves
it 0 too, so only a failed read is negative.

## `9916a70f` — the cost of `--resolve` was understated

Three places said resolution is "one open and one stat per object".
`scan_cl_resolve()` calls `llapi_open_by_fid_at()` twice and `fstat()`
twice for a regular file whose demand mask named a size — the glimpse
takes an open of its own. Corrected in the header comment, the man page
and the commit message, since the sentence exists for a caller to judge
whether to set the flag, and a policy engine is exactly the caller that
asks for a size.

## `f7a82db7` — two more fields with the scanner's lifetime

`struct llapi_scan_rec`'s kernel-doc named `sr_path`, `sr_name` and
`sr_lmm` as the fields a consumer must copy. `scan_cl_obj_free()`
releases `sr_src_name` and `sr_jobid` on the same callback boundary, and
`sr_lmv` and `sr_linkea` are the same shape. All five added, so a
consumer keeping a job id does not keep a dangling pointer.
