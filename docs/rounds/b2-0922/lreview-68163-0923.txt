(1) lustre/utils/libscan_zfs.c (line 333)
    (minor) Could a second scan of the same pool, in the same process, skip the EBUSY checks and read an old import?

    The import is dropped only at kernel_fini(), which runs when scan_zfs_users reaches 0. If another scan is still open (the nesting the scan_zfs_lock comment allows, such as a tool that keeps an MDT scan open while it scans OSTs), this can happen:

        scan X:  dmu_objset_own() ENOENT -> scan_zfs_import() -> spa_import()
        scan_zfs_close(X): disown, users still > 0, spa X stays loaded
        (server: zpool import X, mount, writes)
        scan X again: dmu_objset_own() finds the loaded spa and succeeds

    The second open never reaches the kstat probe or the POOL_STATE_ACTIVE check. It then reads the pool at the first import's uberblock while the server is writing to it, which is the wrong scan that the scan_zfs_import() comment says EBUSY is there to prevent.

    Would it help to run the /proc/spl/kstat/zfs/<pool> probe before every dmu_objset_own()? At least that would catch a pool this host has since imported. If not, could llapi_scan_device(3) document the limit?

(2) lustre/utils/liblustreapi_scan_device.c (line 921)
    (style) This isn't a bug, but this comment no longer matches scan_backend_kind(). A name that begins with '/' goes to ldiskfs whatever it is, a directory included. A relative name that exists as a directory, FIFO or character device goes to ZFS. So 'which never names an existing file' is not what the code relies on. If the patch is refreshed, something like: 'a name beginning with '/', or a relative block device or regular file, is ldiskfs's; any other name is read as a ZFS dataset.'
