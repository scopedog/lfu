(1) lustre/tests/conf-sanity.sh (line 13389)
    (minor) When MDS and OSS are on separate VMs, as in the usual multi-node test clusters, this skips the only successful run of `--local`. `--target` and `--fsname` run only after stopall, where they are expected to fail.

    So no test ever runs the path where `lfs_find_local_targets()` resolves `osd-*/*/mntdev`, splits the label with `lfs_find_label_of()`, and then scans what it found. mds1 alone is enough to cover that before stopall. For example:

        do_facet mds1 "$LFS find --target $(facet_svc mds1) --type f -printf '%LF\n'"
        do_facet mds1 "$LFS find --fsname $FSNAME --mdt $(facet_svc mds1) --type f"

    Checking the exit status and a non-empty answer would do. If the patch is refreshed, worth adding.

(2) include/lustre/lustreapi.h (line 437)
    (suggestion) This isn't a bug, but it puts a second way of asking for the internal objects into the public `struct find_param`. `llapi_find_device()` takes that request as `LLAPI_SCAN_F_INTERNAL` in `sp->lfsp_flags`.

    A library caller that sets `fp_scan_internal = 1` gets no internal objects and no error, because only lfs.c translates the field. `fp_device`, `fp_target`, `fp_fsname` and `fp_local_targets` are the same for `llapi_find()`: they look like search inputs, but the library never reads them.

    Could these CLI-only selectors go in a small lfs-private struct that `lfs_find_parse()` fills alongside `find_param`, so they stay out of lustreapi.h?
