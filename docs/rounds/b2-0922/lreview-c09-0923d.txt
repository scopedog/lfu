(1) lustre/utils/liblustreapi_scan_changelog.c (line 976)
    (defect) With LLAPI_SCAN_CL_F_FOLLOW | _COALESCE | _CLEAR, can one busy file pin the clear point forever?

    A file written more often than sc_min_age (for example a log appended every minute, against the 600s default) goes back to the tail of sl_aged on every event:

        scan_cl_object_one() -> list_del(); scan_cl_absorb(); list_add_tail()

    so scan_cl_flush() never finds it old enough. The sc_max_cached eviction always takes the head, so that never reaches it either. Its co_first stays at its first event, so scan_cl_held_first() caps upto at that index for as long as the file stays busy. Under FOLLOW the end-of-log flush never runs, so the object is never delivered, and the registered user's backlog on the MDT grows without bound until the changelog fills or GC deregisters the user.

    The man page covers the quiet-filesystem case under sc_min_age, but not this one, where the filesystem is active. Would a maximum hold time measured from the first event (deliver once now - first event time exceeds some multiple of sc_min_age) bound it? If this is intended, could the page at least say that a continuously modified object is held indefinitely and blocks clearing?

(2) lustre/utils/liblustreapi_scan_changelog.c (line 1207)
    (minor) sc_endrec is inclusive, but the loop only stops when a record past it arrives. Without FOLLOW the end of the log ends it anyway. With LLAPI_SCAN_CL_F_FOLLOW, the scan delivers record sc_endrec and then blocks in llapi_changelog_recv() until some later record is written, which may be never on an idle MDT. In object mode, everything held also stays undelivered until then. Could the loop break after processing a record with cr_index >= sc_endrec instead?

(3) lustre/utils/liblustreapi_scan_changelog.c (line 389)
    (minor) LLAPI_SCAN_LAZY_SIZE/_BLOCKS are set here for every regular file on the no-glimpse path, whether or not the MDT had a lazy size to give. Take a file with no LSOM, for example one still open for write or on a filesystem with LSOM disabled. ll_getattr_dentry() with AT_STATX_DONT_SYNC then returns i_size as-is, which is 0 for an inode just instantiated by FID, and it only substitutes lli_lazysize when OBD_MD_FLLAZYSIZE is set. That 0 then goes out as a lazy answer. scan_rec_mdt() in liblustreapi_scan.c sets these bits only under OBD_MD_FLLAZYSIZE/FLLAZYBLOCKS. This path is reached by a caller whose sc_want names LLAPI_SCAN_LAZY_SIZE without LLAPI_SCAN_SIZE, or any non-zero sc_want that names a mode or owner but no size. Is there a way to tell a real lazy size apart here, or should the bits stay clear when the value can't be trusted?
