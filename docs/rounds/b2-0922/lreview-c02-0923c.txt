(1) lustre/utils/liblustreapi_scan_device.c (line 433)
    (minor) Do the two scanners really answer alike for a file that was never archived? The comment says they do.

    On a walk, llapi_hsm_state_get_fd() succeeds for any regular file. mdt_attr_get_complex() treats a missing trusted.hsm as -ENODATA and not as an error, so the file comes back with LLAPI_SCAN_HSM set and lfsr_hsm_states == 0.

    Here, the same file has no trusted.hsm, so scan_hsm() returns early and LLAPI_SCAN_HSM stays clear, even though lfsp_got promised HSM on an MDT. A consumer then reads "unknown" from a device scan and "no HSM state" from a walk.

    The xattr was asked for and read, so its absence is a real answer. Should a regular file on an MDT get LLAPI_SCAN_HSM with zero states when XA_HSM was requested but not found?

(2) lustre/utils/liblustreapi_scan_device.c (line 219)
    (minor) A striped directory's shards seem to land here as CLS_VISIBLE.

    lod gives each stripe a normal FID and a trusted.link of its own: the parent is the master, and the name is "<DFID>:<index>". The link test therefore passes, and each shard is delivered by default as a plain directory. scan_lmv_to_user() drops LMV_MAGIC_STRIPE, so nothing in the record marks it as a shard.

    So a directory striped over N MDTs gives 1 record from a walk and N+1 across the device scans. That does not fit the CLS_VISIBLE description in lustreapi.h and llapi_scan_device.3 ("a file or directory a client can name").

    LLAPI_SCAN_LMV_SHARD later in the series (68288) lets a consumer tell them apart. Until then, would it be worth at least saying in the class description that shards are delivered as visible?
