Separately, LLAPI_SCAN_PARAM_MAX_SIZE is named here but is defined only in lustreapi_internal.h, so callers cannot use it. Saying "4096 bytes" would be enough.

(3) lustre/utils/liblustreapi_pfind.c (line 309)
    (minor) Change 68340 (LU-20643 "utils: clear stale lmd fields on reuse") is still open and patches these same two sites, in convert_lmdbuf_v1v2() and in the lstat() fallback of get_lmd_info_fd(). The patchset 9 reply said this fix would go there rather than here. As things stand, whichever change lands second will conflict.

    The two fixes also cover different fields. 68340 clears everything up to lmd_lmm, including lmd_lmmsize and lmd_padding. This change clears only lmd_stx and lmd_fid, so on the fallback path lmd_lmmsize still holds the previous object's value, and llapi_get_lum_file_fd() uses that value as a memcpy() length. That problem predates this patch, but it is exactly what 68340 addresses.

    Should these hunks be dropped in favour of 68340 (with this change based on it), or should 68340 be abandoned and its lmd_lmmsize clear folded in here?

(4) lustre/utils/liblustreapi_scan.c (line 333)
    (minor) The reason this comment gives no longer holds after this patch. It says the lstat() fallback "builds lmd_stx field by field rather than replacing it", but the same patch makes the fallback memset() lmd_stx itself (liblustreapi_pfind.c, just before convert_lmd_statx()), and convert_lmdbuf_v1v2() now does the same. The next sentence then uses that fallback clear as the reason lmd_fid needs no clear here.

    On the ioctl success path, llite copies out a complete statx. On the parent_fd path, the name is written over lmd_stx before the ioctl anyway. So this memset() now looks redundant. If the patch is refreshed, either drop it or reword the comment so it doesn't contradict the fallback.

(6) Documentation/man3/llapi_scan_namespace.3 (line 377)
    (minor) This leaves out one case: a negative value returned by `cb`. llapi_scan_cb_init() sends any non-zero return from ss_cb through the `stop` label into ss_stop_rc, and llapi_scan_namespace() returns it unchanged, so a callback returning -ENOMEM (as layout_cb() in llapi_scan_test.c does) also comes back under <0. It is just as indistinguishable from an errno as the filter's value is. If the page is refreshed, consider "a negative errno on failure, or the negative value `cb` or `lfsp_filter` returned to stop the scan", and in the >0 entry note that it applies to positive `cb` values.
