(1) lustre/utils/liblustreapi_pfind.c (line 2302)
    (defect) Should 'h' be in this set? `%Lh` is a real directive -- documented in lfs-find.1 and handled by printf_format_lustre()'s directory arm -- and it is the only `%L` directive in that arm that is missing here.

    With only `-printf '%Lh'`, find_needs_lmv() is false and this contributes nothing, so find_device_want() leaves LLAPI_SCAN_LMV out of lfsp_want. The scan then never reads trusted.lmv, find_rec_to_lmv() memsets fp_lmv_md and returns early, and the directory arm does:

        hash_type = lum->lum_hash_type & LMV_HASH_TYPE_MASK;  /* 0 */
        if (hash_type < LMV_HASH_TYPE_MAX)
            ... mdt_hash_name[hash_type]

    so every directory prints "none" rather than its real hash type. A walk gets this right because -printf sets gather_all and find_want() asks for the LMV regardless of the format.

    "chiopS" -> "chiopS" plus 'h' looks like the whole fix; 'h' needs only LLAPI_SCAN_LMV, though folding it in with the rest costs nothing.

(2) lustre/utils/liblustreapi_pfind.c (line 3394)
    (minor) Carried over from PS17, where the suggestion was that an object with no LMA still has a derivable FID -- IGIF `INODENUM:GENERATION:0x0` for an MDT inode, IDIF for an OST object -- and the reply was that it would land in the next patchset.

    The commit message now answers the OST half (the object id is in the directory entry, not the inode, so no IDIF), but the MDT half isn't addressed here or in the body: an MDT object with no trusted.lma still prints obj:ID.

    Is the blocker that struct llapi_scan_rec carries no inode generation, so IGIF cannot be built from what the record has? If so, saying that in the commit message alongside the IDIF paragraph would close the thread.
