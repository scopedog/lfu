(3) lustre/utils/liblustreapi_pfind.c (line 5057)
    (minor) Can a later burst change the answer for an object that was rejected? llapi_scan_fid() reads the object as it is now, not as it was at the event, and the log being read was already written when the run began. So the first lookup has already seen every change those later records describe, and a second one differs only if the object changes while the run is in progress.

    The cost is one full lookup per burst for every candidate that does not match:

        find_since_cand_cb()
          -> llapi_scan_fid()   fid2path, statx, common_param_init(), open, getattr
            -> find_since_rec_cb() -> find_since_pick() returns false

    and that includes every changed object outside the root, since the subtree test runs in the callback. With the default sc_min_age of 600s, a file that is written all week and sits outside the subtree is looked up again roughly every ten minutes of the window under `--since 7d`.

    Would setting fso_done after any completed lookup, rejected or not, lose anything?
