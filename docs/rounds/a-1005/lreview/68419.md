## Findings

### 1. `lustre/utils/liblustreapi_pfind.c` (line 5214)

(minor) Can this test ever fire? llapi_find_since() calls find_cookie_read() first, and that already does the fstat() and refuses a non-regular file with the same message and -EINVAL:

    llapi_find_since()
      -> find_cookie_read()     /* fstat(), !S_ISREG -> -EINVAL */
      ...
      -> find_cookie_check()    /* stat(), !S_ISREG -> -EINVAL */

So a directory never reaches here, and the comment above ("the read before it succeeds and returns no anchors") no longer matches the code. The commit message paragraph "A cookie that exists and is not a regular file is refused up front ... while the read succeeds and returns no anchors" says the same thing. If the patch is refreshed, consider dropping this block and keeping the refusal in find_cookie_read(), or keep it here and say it only covers a file swapped between the read and the check.

### 2. `lustre/utils/liblustreapi_pfind.c` (line 5256)

(minor) The stale check runs for every MDT before the first scan, but the scan of MDT N only starts after MDTs 0..N-1 have been read and their candidates looked up, which can take a long time on a big log. If a registered consumer, or changelog_gc, clears past anchor+1 on a later MDT during that time, llapi_changelog_start() starts at the oldest record still there, and the run answers short and advances that MDT's anchor without saying so. That is the case -ESTALE exists for.

The man pages say "Every MDT is checked before any of them is scanned", which is true, but the guarantee only holds when the check runs. Could the scan catch it as well, for example by having llapi_scan_changelog() report the first index it actually read so that a value above sc_startrec leaves the anchors alone and returns -ESTALE? If not, should lfs-find.1 mention the window?

### 3. `Documentation/man3/llapi_find_since.3` (line 75)

(minor) The page never says what fp_since_cookie is. It only shows up as an alternative selector and in the error list. An API caller needs to know that it is a pathname, that the call reads it and then rewrites it (temporary file plus rename(), so it needs write permission on the directory), that a missing file means a first run, and that only one path per cookie makes sense. A short paragraph under "Where to start" next to LLAPI_SINCE_TIME/INDEX would cover it.

Also, -EIO below says only "the cookie could not be read to its end", but llapi_find_since() also returns -EIO when flushing stdout fails, which leaves the cookie as it was.

### 4. `Documentation/man1/lfs-find.1` (line 883)

(suggestion) What happens if the cookie is on the filesystem being searched, e.g. in a home directory on Lustre? Each run makes changelog records of its own: the probe's create and unlink, and the temporary's create and rename over the old cookie. On the next run the renamed temporary looks like a changed object under the root, so the cookie itself matches every time unless the predicates exclude it. The probe and the replaced cookie also count toward the "changed objects no longer exist" warning. The example puts the cookie in /var/lib, which avoids this. Should the text say to keep FILE off the searched filesystem?
