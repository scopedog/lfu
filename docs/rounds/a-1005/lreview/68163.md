## Findings

### 1. `lustre/utils/libscan_zfs.c` (line 181)

(suggestion) For a pool this kernel has imported, the answer is settled before this call. libzpool's pool_active() skips by name every pool that ZFS_IOC_POOL_STATS knows, so zpool_find_config() can only return ENOENT here, and the kstat test below then turns that into -EBUSY.

The cost is that the EBUSY arrives only after zpool_search_import() has opened every device under /dev (or lfsp_search) and read its labels. That is the documented path for `lfs find --target` on a mounted ZFS target, and it also runs for each in-service ZFS target in a `--local` or `--fsname` sweep:

    llapi_find_device() -> llapi_scan_device() -> scan_zfs_open()
      -> dmu_objset_own() == ENOENT -> scan_zfs_import()
      -> zpool_find_config()   /* full label scan */
      -> stat(/proc/spl/kstat/zfs/<pool>) -> -EBUSY

On a server with many disks, every one of those targets pays for a full label scan just to be told it is in use. Could the kstat directory test move ahead of zpool_find_config()? The EINVAL, ENODEV and ENOENT handling after the scan would stay as it is.
