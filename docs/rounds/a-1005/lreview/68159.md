## Findings

### 1. `lustre/utils/liblustreapi_pfind.c` (line 1956)

(minor) On an unstriped directory, this makes a scan print nothing for %Lo, and a walk does not do the same.

On a walk, the unstriped directory gets the one-stripe stub from llapi_scan_get_lmv(). scan_rec_gather_finish() then stores the MDT index in lum_stripe_offset, so the str_cnt == 0 arm prints `[0]`.

On a scan, the directory has no LLAPI_SCAN_LMV, so lfsr_lmvsize is 0 and the test above takes the break. Meanwhile %Li on the same object answers from rec->lfsr_mdt_index (the lum_magic == 0 arm a few lines up).

Should %Lo print `[lfsr_mdt_index]` in that case as well, the way %Li does? If the empty output is intended, should the commit message and llapi_find_device.3 say so? Both currently describe only the striped-directory case.

### 2. `lustre/utils/liblustreapi_pfind.c` (line 3275)

(minor) On a walk, this rejects an object with no birth time under `! -btime` as well as `-btime`, and the -EOPNOTSUPP arm for -newerXb below does the same for the negated `fp_newery[NEWERXY_BTIME][1]` form.

The --projid block earlier in this function chose the opposite for the same situation. There, an object with no project id does not match `--projid N` but does match `! --projid N`, and its comment explains why dropping it from the negated form was wrong.

Is the difference intended? With GNU find, `! -newerBt` is true for a file whose birth time is unknown, because the negation is applied to a false predicate. As it stands, `lfs find $DIR ! -btime -1` silently omits every object that has no birth time (off Lustre, or through the V1 ioctl).
