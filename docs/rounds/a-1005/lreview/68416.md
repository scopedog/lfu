## Findings

### 1. `lustre/utils/liblustreapi_scan.c` (line 1025)

(defect) Should a gather that came back with no FID also be treated as -ESTALE? This guard only runs when LLAPI_SCAN_FID is set, but the gather can succeed without setting it.

The parent (or the directory) is opened with openat(mnt_fd, rp) and the record is filled through get_lmd_info_fd(). If the ioctl answers ENOTTY, that function falls back to lstat_f(path) and zeroes lmd_fid. scan_rec_mdt() then leaves LLAPI_SCAN_FID clear, because a zero FID is not fid_is_sane().

That happens whenever the name fid2path returned now resolves off Lustre. Two ways it can:
- a user who owns a directory on the path swaps it for a symlink between llapi_fid2path_at() and the openat(). openat() follows symlinks in intermediate components and lstat_f() follows them in the composed path.
- another filesystem is mounted over a directory inside the Lustre mount. Path lookup crosses into it, even though the walk starts from mnt_fd.

Either way the call returns 0 and hands cb a record with the stat of a non-Lustre file, labelled with the Lustre path. The commit message promises -ESTALE "rather than a record for a different object". When the caller is root or has CAP_DAC_READ_SEARCH, which this call needs, that record can also expose the size and times of a file the user could not stat.

Once the gather has run, a missing FID can only mean the object found is not the one asked for:
