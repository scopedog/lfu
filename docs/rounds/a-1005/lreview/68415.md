## Findings

### 1. `lustre/utils/liblustreapi_scan_changelog.c` (line 370)

(minor) Should STATX_ATIME and STATX_CTIME be treated the way STATX_MTIME is here?

Without a glimpse they are the MDT inode's values. ll_merge_attr_nolock() merges cat_atime/cat_ctime from the OSTs exactly as it does cat_mtime, and the MDT's ctime only catches up at close (ll_prepare_close() packs ATTR_MTIME and ATTR_CTIME together). So for a file another client is writing, sc_want = LLAPI_SCAN_CTIME gets the MDT's ctime with STATX_CTIME set, while sc_want = 0 gets the OST-merged one, also with STATX_CTIME set. Same field, two different answers, both claimed exact.

Either glimpse when sc_want names LLAPI_SCAN_CTIME or LLAPI_SCAN_ATIME as well, or leave those bits clear when `lazy` is set, as is already done for the mtime.

### 2. `lustre/utils/liblustreapi_scan_changelog.c` (line 1134)

(suggestion) Nothing checks that sc_mnt is a mount of the filesystem sc_mdtname belongs to, although the error message below says it has to be. FIDs are only unique within one filesystem: every filesystem allocates normal sequences from 0x200000400 on, so with two Lustre filesystems mounted, a resolve through the wrong one opens whatever object has that FID there and fills the owner, mode and size from it, with no error.

The fsname is right there in sc_mdtname, so comparing it with llapi_get_fsname() of sc_mnt would be cheap. llapi_root_path_open() also accepts a bare fsname, so a NULL sc_mnt could even default to the fsname taken from sc_mdtname.

### 3. `Documentation/man3/llapi_scan_changelog.3` (line 359)

(minor) "The MDT's either way" is only right when there is no glimpse. When the demand mask is 0 or names a size, blocks or mtime, ll_glimpse_size() goes through ll_merge_attr(), which also raises atime and ctime to the OST objects' values. If the code is left as it is, maybe say the atime and ctime are exact only when the OSTs were glimpsed.
