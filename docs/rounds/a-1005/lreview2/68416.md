## Findings

### 1. `lustre/utils/liblustreapi_scan.c` (line 1026)

(minor) "A gather that ran and found no FID found something off Lustre" leaves out one more case: client modules that only have the V1 getinfo ioctl. get_lmd_info_fd() falls back to IOC_MDC_GETFILEINFO_V1 / LL_IOC_MDC_GETINFO_V1, and convert_lmdbuf_v1v2() zeroes everything before lmd_lmm, lmd_fid included:

    memset(lmd_v2, 0, offsetof(typeof(*lmd_v2), lmd_lmm));

A zero FID is not fid_is_sane(), so scan_rec_mdt() never sets LLAPI_SCAN_FID, and every llapi_scan_fid() call with a non-name-only mask returns -ESTALE. The intended --since consumer reads -ESTALE as "gone since the event", so every object would be dropped silently.

The library still carries that fallback (scan_rec_mdt() sizes the layout specially for it). If the combination still matters, could it return something other than -ESTALE there, such as -EOPNOTSUPP? If it doesn't, the comment and the -ESTALE text in llapi_scan_fid.3 could at least name the case.

### 2. `Documentation/man3/llapi_scan_fid.3` (line 56)

(minor) "answers relative to the filesystem root" conflicts with the paragraph just above ("because that name is relative to it", i.e. the mount root) and with the kernel-doc ("That name is relative to the mount root"). __ll_fid2path() sends ll_inode2fid() of mnt_fd as gf_root_fid, and mdt_path_current() stops at that FID. On a fileset (subdirectory) mount the answer is therefore relative to the mount, not to the filesystem root. Composing <mnt_path>/<rel> is correct because of that, so only the wording is off. The same phrase is in the inline comment above the trailing-slash trim in llapi_scan_fid(). If the patch is refreshed, "relative to the mount root" in both places would match the code.
