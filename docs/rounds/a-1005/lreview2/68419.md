## Findings

### 1. `lustre/utils/liblustreapi_pfind.c` (line 5951)

(minor) Is the highest index seen a safe resume point while the MDT is still being written to?

mdd_changelog_write_rec() hands out lrh_index and cr_index under lgh_lock, then drops the lock before the record is written ("drop the loghandle semaphore for parallel writes"). The bitmap bit is set only after dt_record_write() returns:

    rec->cr.cr_index = ++mdd->mdd_cl.mc_index;
    up_write(&loghandle->lgh_lock);
    ...dt_record_write(...)
    __test_and_set_bit_le(r->lrh_index, LLOG_HDR_BITMAP(...));

So the writer of N+1 can set its bit while the writer of N is still copying. llog_process_thread() skips any index whose bit is clear (llog_is_index_skipable()). A run that reaches the tail in that window delivers N+1 without N, and fss_reached becomes N+1. The next run starts at N+2, and mdc_changelog skips everything below crs_start_offset, so N is never reported. The stale check cannot catch this.

The window is small, but a cookie job runs over and over on a busy MDT, and the commit message promises that a cookie "is exact on every MDT". Could the anchor stop short of the tail, e.g. at the last index of an unbroken run, or keep a small margin and let _ONCE drop the repeats? Failing that, could the man page state the limit?

### 2. `lustre/utils/liblustreapi_pfind.c` (line 5096)

(minor) What happens when the cookie lives inside the tree being searched, e.g. `lfs find /mnt/lustre --since-cookie /mnt/lustre/.job.ck`?

The pre-pass probe creates and unlinks a temporary, and find_cookie_write() creates another and renames it over the cookie. On Lustre each of those is a changelog record with an index above the anchor this run just wrote. So the next run always gets the cookie's FID as a candidate: it resolves under the root and prints the cookie path (any search without a predicate that excludes it matches it), and the probe's unlinked temporary adds to the "changed objects no longer exist" warning. That repeats on every run.

Could the run skip the cookie's own FID, or could lfs-find.1 at least say to keep the cookie outside the filesystem being searched?

### 3. `lustre/utils/liblustreapi_pfind.c` (line 4911)

(minor) Only find_cookie_write() produces this file, and it always writes "under <root>". A header with no root comes from an earlier patchset's format, which never reached master. Keeping the `oldroot == NULL` acceptance means a header with the root removed, whether by hand or by any other cause, silently skips the subtree binding this check exists to enforce. If the patch is refreshed, should a header without " under " be refused like a wrong fsname?
