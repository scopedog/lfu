## Findings

### 1. `lustre/utils/liblustreapi_pfind.c` (line 5189)

(defect) Does _ONCE dedup across MDTs here? sl_seen belongs to one llapi_scan_changelog() call and is freed when that call returns. This loop makes one call per MDT, so an object that two MDTs' logs name is a candidate twice: llapi_scan_fid() runs twice and the path prints twice.

On DNE this is routine. Namespace records go to the MDT that served the request, and attribute records go to the MDT holding the inode:

    lfs mkdir -i 1 $MOUNT/d1; chmod 700 $MOUNT/d1
        CL_MKDIR on MDT0000, CL_SETATTR on MDT0001
    touch $MOUNT/d0/f; mv $MOUNT/d0/f $MOUNT/d1/   (d0 on MDT0, d1 on MDT1)
        CL_CREAT on MDT0000, CL_RENAME with cr_sfid = f on MDT0001

Each object prints twice from `lfs find $MOUNT --since 1h`, but a walk prints it once. The commit message says --since "reaches it once per FID and prints it once", and the comment above gives the same reason for _ONCE.

The FID set has to outlive the per-MDT call. That could be a seen-set in find_since_state tested in find_since_cand_cb(), or a way to share one set between the llapi_scan_changelog() calls.

### 2. `lustre/utils/liblustreapi_pfind.c` (line 5162)

(minor) This repeats find_mount_is_fileset(), which is earlier in this file, but leaves out its fid_is_igif() exception. A filesystem upgraded from before 2.4 has an IGIF root FID, so every plain mount of it counts as a fileset here. The "no longer exist" warning then adds ", or are outside this fileset," when there is no fileset. If the patch is refreshed, could this be `find_mount_is_fileset(mnt_path) == 1`?

### 3. `lustre/utils/liblustreapi_pfind.c` (line 5222)

(style) This isn't a bug, but "N objects were dropped with it" has nothing for "it" to refer to when it is printed. The error it means comes later, from lfs_find()'s "failed for '<path>'". Naming the error here would let the line stand alone, e.g. "%llu changed objects could not be checked and are not in the answer: rc = %d" with st.fss_scan_rc.
