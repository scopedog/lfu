LU-20603 · liblustreapi · since 2.18.0

llapi_scan_namespace()

Walk a Lustre namespace and get one record per object, instead of a line of text to parse. The scanner fetches only the fields you say you will read, and tells you which ones it could actually answer for.

#include <lustre/lustreapi.h> -llustreapi client side

What it is, and when to reach for it

This is the programmatic form of what lfs find does: the same traversal, the same attribute gathering, delivered to your callback rather than judged against command-line predicates and printed. It exists so that a tool needing per-object attributes does not have to shell out to lfs find and parse its output, nor reimplement the ioctl sequence that gathering them correctly requires.

If you want to…UseRuns on
Search a mounted filesystem from a shelllfs findclient
Search a mounted filesystem from a programllapi_scan_namespace()client
Pull that scan's records in batches insteadllapi_scan_next()client
Read an unmounted MDT or OST off its block devicellapi_scan_device()server
Run lfs find's predicates against such a devicellapi_find_device(), or lfind(8)server
Fill a record for one object you already have a FID forllapi_scan_fid()client
This one is client side

It walks a namespace, so there has to be a Lustre mount to walk — which means a client. It is the programmatic form of lfs find, and lfs find is a client command by construction: llapi_is_lustre_mnt() requires ":/" in the mount's device name, so a server target mount is deliberately not recognised.

The server-side counterpart is llapi_scan_device(), which reads a target's objects straight off its block device with no mount at all. Both live in liblustreapi and a client build carries both symbols — but a client has no backend plugin, so a device scan there returns -ENOTSUP. The lfind(8) command is built under SERVER and is not shipped to clients.

All five share one gather path and one record definition, which is the subject of a companion page. Everything below concerns the namespace scanner specifically.

The call

lustre/lustreapi.h
typedef int (*llapi_scan_cb_t)(const struct llapi_scan_rec *rec, void *data);

int llapi_scan_namespace(const char *path,
                         const struct llapi_scan_param *sp,
                         llapi_scan_cb_t cb, void *data);

The callback runs once per object below path, receiving a record and your data unchanged. sp may be NULL for the defaults.

ReturnMeaning
0The walk finished.
> 0A callback stopped the scan. The value is whatever that callback returned, passed back unchanged.
< 0A negative errno.

A worked example

Find the regular files under /data owned by tanjiro and modified in the last thirty minutes. As a command that is:

the shell equivalent
$ lfs find /data -user tanjiro -mtime -30m -type f

As a program it is the following, complete and compilable. Three things in it are the whole API in miniature: sp_want asks for exactly the three fields the test reads, the callback checks the record's mask before trusting any of them, and the username is resolved once rather than per object.

recent.c — cc -o recent recent.c -llustreapi
#include <lustre/lustreapi.h>
#include <pwd.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <time.h>

struct recent {
        __u32   uid;      /* tanjiro, resolved once */
        __s64   since;    /* epoch seconds, 30 minutes ago */
        __u64   found;
};

/* The three fields this test reads.  Ask for exactly these: anything
 * more is an ioctl or an open per object that nothing will look at.
 */
#define WANT (LLAPI_SCAN_UID | LLAPI_SCAN_MTIME | LLAPI_SCAN_MODE)

static int recent_cb(const struct llapi_scan_rec *rec, void *data)
{
        struct recent *r = data;

        /* A field the scanner could not answer for is not a match.  Test
         * the bits; do not compare the fields against zero, because "no
         * answer" and "the answer is zero" are different things here.
         *
         * These three live in the embedded statx, so the mask that
         * reports them is sr_stx.stx_mask -- and LLAPI_SCAN_UID and its
         * kind ARE the STATX_* values, so one vocabulary asks and the
         * right mask answers.
         */
        if ((rec->sr_stx.stx_mask & WANT) != WANT)
                return 0;

        if (!S_ISREG(rec->sr_stx.stx_mode))
                return 0;
        if (rec->sr_stx.stx_uid != r->uid)
                return 0;
        if (rec->sr_stx.stx_mtime.tv_sec < r->since)
                return 0;

        printf("%s\n", rec->sr_path);
        r->found++;

        return 0;               /* keep going */
}

int main(void)
{
        struct llapi_scan_param sp = {
                .sp_size = sizeof(sp),   /* required */
                /* WANT is the three flags above: LLAPI_SCAN_UID |
                 * LLAPI_SCAN_MTIME | LLAPI_SCAN_MODE, so the scan
                 * gathers the uid, the mtime and the mode, and
                 * nothing else.
                 */
                .sp_want = WANT,
        };
        struct recent r = { .found = 0 };
        struct passwd *pw;
        int rc;

        pw = getpwnam("tanjiro");
        if (pw == NULL) {
                fprintf(stderr, "no such user: tanjiro\n");
                return 1;
        }
        r.uid = pw->pw_uid;
        r.since = (__s64)time(NULL) - 30 * 60;

        rc = llapi_scan_namespace("/data", &sp, recent_cb, &r);
        if (rc < 0) {
                fprintf(stderr, "scan of /data failed: %s\n", strerror(-rc));
                return 1;
        }

        printf("%llu file(s)\n", (unsigned long long)r.found);

        return 0;
}
Why LLAPI_SCAN_MODE and not LLAPI_SCAN_TYPE

LLAPI_SCAN_TYPE is free — it comes from the directory entry — but it is set only when the entry knew the object's type, which not every filesystem fills in. This scan pays for an ioctl anyway to get stx_uid and stx_mtime, and stx_mode arrives with them, so testing the full mode costs nothing extra and is always answerable. In a scan that wants only the type, ask for LLAPI_SCAN_TYPE and pay no ioctl at all.

Scaling it up is a one-line change: set sp_thread_count and take a lock around r->found. See Threads & stopping.

When the callback runs

Once per object the walk reaches — files and directories alike, including the path you started from. For a directory it is called on the way down, before its children. What follows is every way an object can be reached and still not be delivered, in the order llapi_scan_cb_init() tests them.

Skipped whenWhat happens to the walk
A consumer already stopped the scan Nothing further is gathered, no directory is descended, and the callback is not called again. Enforced in the scanner rather than left to the traversal, which without LLAPI_SCAN_F_STOP_ON_ERROR would note the value and carry on — and with several threads the other workers would know nothing about it.
The object is above sp_min_depth Not delivered; the walk still descends.
sp_filter returned > 0 Not gathered and not delivered; a directory is still descended into. A negative return stops the whole scan instead.
It was unlinked between readdir and the gather — -ENOENT or -ESTALE Skipped as normal, not as an error: it existed when the directory was read and does not now.
The gather failed some other way — a permission problem, an ioctl error Skipped silently, unless sp_flags carries LLAPI_SCAN_F_STOP_ON_ERROR, which makes it end the scan.
The object is below sp_max_depth Never visited: the traversal stops descending at the limit.
A skip is not an error, and you will not hear about it

The unlinked and failed-gather cases are invisible to the consumer: no callback, and no counter in the namespace scanner. A search that must tell no matches from could not look has to set LLAPI_SCAN_F_STOP_ON_ERROR. llapi_scan_device(3) is the other way round — it counts skips in ss_skipped, because torn reads off a live target are expected there and have to be visible.

Delivery does not mean the record is complete. The gather succeeding says the object was read, not that every field you asked for arrived — which is what the masks are for. A file whose i_extra_isize does not reach i_crtime genuinely has no birth time, and its record arrives without STATX_BTIME in sr_stx.stx_mask.

One asymmetry is worth holding on to: the pre-filter sees only what the directory entry knew — sr_path, sr_name and the type derived from d_type. Anything else you would reject on has to wait for the callback, by which point the gather has already been paid for.

Reading the record

struct llapi_scan_rec carries the object. What stat(2) answers for is an embedded struct statx, in the form the MDT already fills; the Lustre-specific fields are the record's own. Two fields make it survivable across library versions, and one rule governs reading all the others.

The record begins with that statx, so a struct llapi_scan_rec * may be cast to a struct statx * and handed to anything that takes one. &rec->sr_stx says the same thing at the same cost; the Lustre-specific fields follow past offset 0x100.

FieldPurpose
sr_sizeHow much of the record this scanner filled. Fields are only ever appended, so a consumer built against an older definition keeps working. It sits after sr_stx, so it is found at an offset sizeof(struct statx) decides — see the note below.
sr_stxThe mode, nlink, uid, gid, size, blocks and the four timestamps — whole struct statx_timestamp, so an incremental scan keyed on stx_mtime has the nanoseconds the MDT recorded.
sr_stx.stx_maskWhich of those fields are set. The low 32 LLAPI_SCAN_* bits are the kernel's STATX_* values, aliased rather than copied, so the two cannot drift.
sr_validWhich of the API's own fields are set — FID, layout, LMV, HSM, project id, class, the changelog event. These bits live above bit 31; sr_valid's low half is reserved and always zero.
The one rule

Test the bit; never compare the field against zero. A scanner that could not answer and a scanner that answers zero mean different things, and the record distinguishes them deliberately.

Test it against the right mask: sr_stx.stx_mask for anything inside the statx, sr_valid for the rest. Both halves are named in one vocabulary, so sp_want takes either — but a test of sr_valid against LLAPI_SCAN_SIZE compiles cleanly and is always false.

What the statx-first layout costs

Every Lustre field sits at an offset sizeof(struct statx) decides. The library asserts at build time that the statx is still the 256 bytes it has been since Linux 4.11, and that sr_stx starts the record — because a statx that grew would move the rest of the struct under a consumer already built against it, and sr_size reports how much of a record was filled, never that a field moved. A binding written in another language has no such assertion: it must model those 256 bytes exactly before it can reach any field beyond them.

The clearest case is a regular file's size. File data lives on OSTs, so in the general case the size is not the MDT's to give — STATX_SIZE stays clear in stx_mask rather than reporting 0. When the MDT holds a lazy size-on-MDT value instead, LLAPI_SCAN_LAZY_SIZE in sr_valid says so and the number is in sr_stx.stx_size — the value is there and it is the MDT's approximation, which is exactly why stx_mask does not claim the field. A consumer needing a strict size for every regular file must stat it, which is what lfs find --size does — and why sr_parent_fd and sr_name are in the record, so you can do it with fstatat(2).

The same distinction runs through HSM: state 0 with LLAPI_SCAN_HSM set means the scan asked and the file has no HSM state, which is not the same as the bit being clear.

The parameter block

sp_size must be set — it is how the library knows which fields you built against. A struct shorter than the library's is accepted and the fields you did not set read as zero. A longer one is accepted too, as long as every byte past the end of that library's definition is zero: which is you saying you set no field it could not honour. Set one of them and the call is refused with -EINVAL.

So the size is not a version number. A program built against a newer header runs against an older library for as long as it asks only for what that library has, and a field appended here does not break the programs that do not use it.

FieldDefaultMeaning
sp_size—Required. sizeof(struct llapi_scan_param).
sp_want0Demand mask. 0 means everything except the three opt-in fields below.
sp_gotNULLFilled, before the first record, with the part of sp_want this scan will answer for. See the demand mask.
sp_max_depth0Limit the descent. 0 is unlimited.
sp_thread_count00 or 1 scans in the calling thread.
sp_flags0LLAPI_SCAN_F_STOP_ON_ERROR abandons the scan on an unreadable object instead of skipping it.
sp_filterNULLPre-I/O filter. See below.
Unknown flags are refused, unknown fields are not

An sp_flags bit this library does not define returns -EINVAL. Setting a flag does not change sp_size, so refusing unknown ones is what gives flags the same guarantee fields have: a caller never has one silently dropped.

sp_want is the opposite case and is not refused. A flag is commanded, where a field is asked for — so a want bit this library does not know, or knows but this scan cannot answer for, is dropped, and sp_got reports what is left.

The library reads every byte you declare

Accepting a longer struct means reading past the end of the library's own definition, on your word that sp_size describes memory you own. A block that declares more than it has — sp_size = sizeof(sp) + 8 on a plain struct, say — is read out of bounds. Three cases in our own test suite did exactly that, and passed only because the stack bytes behind them happened not to be zero.

The demand mask

sp_want names the fields you will read. It exists because the same field is not the same cost to every scanner, and because a consumer that asks for everything makes the cheap scans expensive.

Ask forCostsNotes
LLAPI_SCAN_TYPEnothingThe directory entry already knew. This is LLAPI_SCAN_DIRENT_MASK.
Most attribute fieldsone ioctl per objectMode, uid, gid, times, layout, directory stripe.
LLAPI_SCAN_MDT_INDEXan open per objectGathered only when named, because each costs an open or an ioctl of its own. A scanner reading a target's inodes directly answers all three for free — which is why the mask exists.
LLAPI_SCAN_PROJIDan open per object
LLAPI_SCAN_HSMan ioctl per object

A scan wanting nothing outside LLAPI_SCAN_DIRENT_MASK performs no ioctl per object at all — that is what makes a name-only search cheap.

a name-only scan: no ioctl per object
struct llapi_scan_param sp = {
        .sp_size = sizeof(sp),
        .sp_want = LLAPI_SCAN_TYPE,
};
The mask is a floor, not a ceiling

A field you did not ask for may still be delivered — the mask says what you need, not what you will get. Always test the record's masks rather than assuming a field is present because you asked, or absent because you did not.

What the scan answers back

Asking is one half; the other is being told what will arrive. Point sp_got at a __u64 and the scan fills it, before the first record, with the part of sp_want it will answer for. An unknown bit, or one this particular scan cannot supply, is simply absent from it.

ask for what you would use, adapt to what you get
/* The parent FID is what this consumer would rather name an object by:
 * a scan of a target reads it out of the object's linkea, where a walk
 * of a namespace has no notion of it.  Ask for it anyway -- a field
 * this scan cannot answer for is dropped, not an error -- and let
 * sp_got choose the branch.
 */
#define WANT (LLAPI_SCAN_MODE | LLAPI_SCAN_FID | LLAPI_SCAN_PARENT)

struct ctx {
        __u64           got;    /* filled before the first record */
        unsigned long   named;
};

static int name_cb(const struct llapi_scan_rec *rec, void *data)
{
        struct ctx *c = data;

        /* A test of what the scan settled once, not of this record: every
         * record in one scan takes the same branch.  The record's own
         * masks are still what you test for a per-object field.
         */
        if (c->got & LLAPI_SCAN_PARENT)
                name_by_parent(&rec->sr_parent_fid, rec->sr_name);
        else
                name_by_path(rec->sr_path);

        c->named++;

        return 0;
}

struct ctx c = { 0 };
struct llapi_scan_param sp = {
        .sp_size = sizeof(sp),
        .sp_want = WANT,
        .sp_got  = &c.got,
};

int rc = llapi_scan_namespace("/data", &sp, name_cb, &c);

/* Here sp_got comes back as LLAPI_SCAN_FID | LLAPI_SCAN_MODE -- no
 * LLAPI_SCAN_PARENT -- so every object took the sr_path branch.  The
 * same consumer handed to llapi_scan_device() on an MDT is told
 * LLAPI_SCAN_PARENT and takes the other one, unchanged.
 */

A consumer that can do nothing useful without a field refuses rather than adapts. sp_got is filled before the first record, so the first callback is the earliest place to act on it — and a negative return there stops the scan and comes back to the caller unchanged, so finding out costs one object's gather rather than a walk of the tree.

or refuse, at the cost of one object
#define NEED (LLAPI_SCAN_PROJID | LLAPI_SCAN_HSM)

static int audit_cb(const struct llapi_scan_rec *rec, void *data)
{
        struct audit *a = data;

        if (!a->checked) {
                a->checked = 1;
                if ((a->got & NEED) != NEED)
                        return -ENOTSUP;  /* the scan returns it to you */
        }

        report(rec->sr_projid, rec->sr_hsm_states);

        return 0;
}
It is the scan's answer, not the library's

What can be answered depends on which entry point you called and on what it opened, so sp_got is filled per scan rather than being a property of the build. llapi_scan_device() fills it once it has read the target's label: a scan of an OST reports LLAPI_SCAN_OWNER, a scan of an MDT reports LLAPI_SCAN_LMV and LLAPI_SCAN_LAYOUT instead, and LLAPI_SCAN_MDT_INDEX appears only where the label carried an index. With sp_want at 0 it reports what the scanner's own default came to.

A bit in sp_got says the scan may fill the field, not that any one object has it — a file with no project id still leaves LLAPI_SCAN_PROJID clear in sr_valid. What it buys you is learning once that a field will never arrive, instead of inferring it object by object and never being sure.

Threads, and stopping early

sp_thread_count of 0 or 1 scans in the calling thread. Above that, the callback runs concurrently on several threads and must be thread-safe. The record passed to each call is private to that call; data is shared between them, and locking it is yours to do.

four threads, stopping at the first match
static int first_cb(const struct llapi_scan_rec *rec, void *data)
{
        if (!(rec->sr_stx.stx_mask & STATX_UID) || rec->sr_stx.stx_uid != 0)
                return 0;

        /* Non-zero stops the scan and is returned to the caller
         * unchanged, so pick a value you will recognise.
         */
        return 1;
}

struct llapi_scan_param sp = {
        .sp_size         = sizeof(sp),
        .sp_want         = LLAPI_SCAN_UID | LLAPI_SCAN_FID,
        .sp_thread_count = 4,
};

int rc = llapi_scan_namespace(path, &sp, first_cb, &found);
/* rc == 1 : stopped by the callback
 * rc == 0 : the walk finished, nothing matched
 * rc <  0 : negative errno
 */

With several threads the scan does not stop the instant a callback returns non-zero — the others finish the object in hand. Expect a few more callback invocations after the one that stopped it.

Pulling records in batches

The callback is a push: the scan calls you, on whichever of its threads produced the object. Some consumers want the opposite — their own thread, their own loop, many records per call. That is the same scan turned around, through a handle.

lustre/lustreapi.h
struct llapi_scan_handle;

int llapi_scan_namespace_open(const char *path,
                              const struct llapi_scan_param *sp,
                              unsigned int batch, void *data,
                              struct llapi_scan_handle **hp);
int llapi_scan_next(struct llapi_scan_handle *h,
                    const struct llapi_scan_rec *const **recs,
                    unsigned int *nrecs);
int llapi_scan_close(struct llapi_scan_handle *h);

batch is the most records one llapi_scan_next() returns, 0 asking for the default of 1024. The scan runs on a thread of its own and fills one batch while you hold the other, blocking when its own is full — so it runs at most one batch ahead and the memory in flight is bounded by batch, not by the size of the tree. The parameter block is the same one, validated the same way, and sp_filter still runs on the scan's threads with your data.

count.c — cc -o count count.c -llustreapi
#include <lustre/lustreapi.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>

int main(void)
{
        struct llapi_scan_param sp = {
                .sp_size         = sizeof(sp),
                .sp_want         = LLAPI_SCAN_MODE,
                .sp_thread_count = 4,
        };
        const struct llapi_scan_rec *const *recs;
        struct llapi_scan_handle *h;
        unsigned int n, i;
        __u64 files = 0;
        int rc;

        /* Starts the scan.  Only what llapi_scan_namespace() refuses at
         * once -- a bad sp_size, an unknown flag -- is refused here; a
         * path that does not exist is reported by the first _next().
         */
        rc = llapi_scan_namespace_open("/data", &sp, 1024, NULL, &h);
        if (rc < 0) {
                fprintf(stderr, "cannot start the scan: %s\n", strerror(-rc));
                return 1;
        }

        /* n == 0 with rc == 0 means the scan ended.  The records, and
         * everything they point at, belong to the handle and are released
         * by the NEXT call -- so anything kept past the loop body is
         * copied here, exactly as it would be inside a callback.
         */
        while ((rc = llapi_scan_next(h, &recs, &n)) == 0 && n > 0) {
                for (i = 0; i < n; i++) {
                        const struct llapi_scan_rec *rec = recs[i];

                        if ((rec->sr_stx.stx_mask & STATX_MODE) &&
                            S_ISREG(rec->sr_stx.stx_mode))
                                files++;
                }
        }
        if (rc < 0)
                fprintf(stderr, "scan failed: %s\n", strerror(-rc));

        /* Stops a scan still running, frees the handle and every batch it
         * handed out, and returns what the scan itself returned.
         */
        rc = llapi_scan_close(h);

        printf("%llu file(s)\n", (unsigned long long)files);

        return rc < 0;
}

A batch record is the record the callback would have been given, with two differences. Everything it points at is the batch's own copy, valid until the next llapi_scan_next() rather than for the length of one call. And sr_parent_fd and sr_fd are -1: they are the scan's descriptors, closed when it moves on, and a batch of open descriptors would be a batch of leaks waiting on the consumer.

What the copy costs, measured

A callback record points into buffers the scan reuses for the next object, so a record that outlives its callback has to own what it points at — the path, the name, the layout, the directory stripe, the linkea. That copy is the whole cost of a batch, and next to an MDT ioctl it is small:

ThreadsBatchCallbackBatchOver
110242744.1 ms2755.4 ms+0.4%
41024938.2 ms951.8 ms+1.4%
41947.5 ms1114.4 ms+17.6%

20,021 objects on ldiskfs, medians of 15 alternating runs. On a tree whose records carry layouts the difference falls inside the noise (+0.5% at four threads, −0.8% at one). Off Lustre, where the per-object work is a cached lstat(2) and the copy is the largest share it will ever be, the same batch costs +5–8% — that is the upper bound, not the figure.

The row to avoid is a batch of 1. It pays a lock round trip per record and removes nothing: use the callback instead, which is what that shape is.

Records arrive in the order the scan's threads produced them, which above one thread is not a namespace order — the same as the callback, where nothing promised an order either. An error is reported only after every record produced before it has been handed out, so the batches you already have are whole.

Which one to reach for

The callback, unless something makes it awkward. A batch is worth its copy when the consumer has a thread of its own it must run on — a language runtime that cannot be called into from a foreign thread, a main loop that owns the data structure being filled — or when records are handed straight to something that already takes an array.

The pre-filter

sp_filter is called before any I/O on the object, with a record carrying only sr_path, sr_name and — when the directory entry knew it — LLAPI_SCAN_TYPE. It is how you get the cheap-rejection behaviour lfs find has internally: reject on the name, and never pay for the attributes.

ReturnEffect
0Gather the object and deliver it to the callback.
1Skip it without gathering. Descent into a directory is unaffected.
< 0Stop the scan.
only *.log, decided before any I/O
static int only_logs(const struct llapi_scan_rec *rec, void *data)
{
        const char *dot;

        /* Directories still have to be descended into.  Returning 1 for
         * one would skip the directory itself, not its contents -- but
         * there is no reason to skip it here.
         */
        if ((rec->sr_stx.stx_mask & STATX_TYPE) &&
            S_ISDIR(rec->sr_stx.stx_mode))
                return 0;

        dot = rec->sr_name ? strrchr(rec->sr_name, '.') : NULL;

        return (dot && strcmp(dot, ".log") == 0) ? 0 : 1;
}

sp.sp_filter = only_logs;

Layouts and directory stripes

Layouts arrive raw, as sr_lmm and sr_lmmsize, for you to decode with llapi_layout_get_by_xattr(3). A directory's stripe arrives the same way as sr_lmv and sr_lmvsize, under LLAPI_SCAN_LMV, which is set only for a directory that has one.

decode a copy, never the record's own buffer
/* llapi_layout_get_by_xattr() takes a NON-const pointer and may
 * byte-swap in place.  The record's buffer belongs to the running
 * scan, so swabbing it would corrupt the walk.
 */
void *buf;

if (!(rec->sr_valid & LLAPI_SCAN_LAYOUT) || rec->sr_lmm == NULL)
        return 0;

buf = malloc(rec->sr_lmmsize);
if (buf == NULL)
        return -ENOMEM;

memcpy(buf, rec->sr_lmm, rec->sr_lmmsize);
layout = llapi_layout_get_by_xattr(buf, rec->sr_lmmsize, 0);

One object, by FID

A walk is the wrong shape when you already know which object you want. llapi_scan_fid() fills the same record for a single FID through a mount, using the same gather everything above describes — so a consumer that got a FID from somewhere else answers the same questions a walk answers, rather than from a stat(2) of its own that covers a fraction of them.

lustre/lustreapi.h
int llapi_scan_fid(int mnt_fd, const char *mnt_path,
                   const struct lu_fid *fid,
                   const struct llapi_scan_param *sp,
                   llapi_scan_cb_t cb, void *data);

mnt_fd is an open descriptor on a client mount of the filesystem the FID belongs to, as llapi_root_path_open(3) returns, and mnt_path is that mount’s path. Both are required, and a caller filling records for many FIDs opens the mount once and passes the same pair to each call. The callback runs once, with the same lifetime rule as everywhere else on this page: the record is valid for the duration of the call and nothing in it outlives it.

Only three fields of the parameter block mean anything here. sp_want is the demand mask, as above; sp_got reports what this call will answer for, as above; sp_filter runs before the gather, as above. The rest — sp_max_depth, sp_stats, sp_search, sp_flags — describe a traversal there is none of and are ignored, so one block can be shared with a walk. An sp_thread_count above 1 is refused rather than ignored, because a caller setting it has misunderstood the call.

What it costs, and what it needs

The FID is resolved with llapi_fid2path(3) and the record gathered at the resulting pathname, so the caller needs what that needs: CAP_DAC_READ_SEARCH, unless llite.*.user_fid2path is set. That is one lookup per object on top of the gather — roughly two round trips where a walk pays one — which is the price of asking about objects a walk would have to find first.

An object unlinked since the caller learned of it no longer resolves and comes back -ENOENT. For a consumer asking what is true now, that is the answer rather than an error to work around.

It fills a fresh record and reads nothing in from the caller. A consumer merging the result into a record it already holds decides for itself which fields it lets this call supply — which is how llapi_scan_changelog(3) keeps answering as recorded while filling in what an event never carried.

Its first consumer is lfs find --since, where the changelog supplies candidates and this call verifies each one against the live object, so every predicate keeps the meaning it has without the flag.

ValueCause
-EINVAL path or cb is NULL; or sp_size is smaller than the fields up to and including sp_want, or larger than the library's definition with a byte past the end of it set; or sp_flags sets a bit this library does not define.
-ENAMETOOLONG path is longer than PATH_MAX.

Traps

TrapWhat happens
Keeping the record It is valid only for the duration of the callback. Copy anything you keep — including whatever sr_path, sr_name, sr_lmm and sr_lmv point at.
Keeping a batch past the next llapi_scan_next() The batch owns its copies and releases them on the next call. The rule is the callback's, one batch wide rather than one record wide.
Keeping a descriptor sr_parent_fd and sr_fd are the scan's own and are closed when it moves on. Use them inside the callback, or dup(2) them. In a batch they are -1.
Testing a field against zero You cannot tell "no answer" from "the answer is zero". Test the bit.
Testing the wrong mask sr_valid & LLAPI_SCAN_SIZE and stx_mask & LLAPI_SCAN_FID both compile and are both always false. Statx fields report through sr_stx.stx_mask, the rest through sr_valid.
Forgetting sp_size -EINVAL. It is not optional even when every other field is left at its default.
Overstating sp_size The library reads the bytes you declare. A block whose sp_size is larger than the storage behind it is read out of bounds — and refused with -EINVAL if what it reads there is not zero, which is the right answer arrived at for the wrong reason.
Reading sp_got as a promise about an object It says the scan may fill the field, not that any given object has it. The record's own masks are still what you test per object.
Decoding sr_lmm in place llapi_layout_get_by_xattr() may swab the buffer it is given, and that buffer belongs to the running scan.
Sharing data without a lock Above sp_thread_count 1 the callback runs concurrently. The record is private per call; data is not. A batch is handed to one thread, so its loop needs no lock — but sp_filter still runs on the scan's threads.
