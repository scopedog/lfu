The lfs find rewrite

lfs find had one 586-line function that gathered an object's attributes and judged them in the same breath. Splitting the two produced a record any consumer can read — and made a scanner API possible without a second copy of the vocabulary.

Lustre 2.18 / 2.19 liblustreapi Behaviour unchanged

The shape that changed

Nothing here is a performance story. The rewrite exists because lfs find knew how to ask an MDT about an object and no other caller could reach that knowledge without copying it. The measurements below are line counts and call sites, not throughput.

One function, 586 lines

The traversal called cb_find_init() once per object, and that one function did everything: read what the directory entry knew, decide which ioctls the search needed, issue them, run every predicate against the results, and print. The steps were interleaved on purpose — a name that cannot match should not cost an ioctl — and interleaving them is what made the function impossible to reuse.

Why it resisted sharing

The fetched attributes never existed as a value. They lived in param->fp_lmd, a buffer owned by the search, mutated in place, and read by predicates that also consulted the traversal's local variables — the parent descriptor, the dirent, the depth.

A second consumer could not call in halfway. It would have had to reproduce the gathering, which is where the knowledge actually was.

What the split had to preserve

The interleaving. If gathering became a phase that ran to completion before deciding began, every lfs find -name would pay an ioctl per object for attributes it was about to discard.

So the new shape is not gather-then-decide. It is decide-what-to-gather, gather that, then decide — with the demand mask carrying the answer between the halves.

Five stages, two of them shared

The walk now runs five stages per object. The first two are free; the third names a price; the fourth pays it; the fifth judges. Only the third and fifth are new code — and both are shared.

1 scan_rec_dirent() What readdir already told us: path, name, and the object type when the entry carried one.
2 find_prefilter() Predicates that need nothing else. A non-matching -name exits here, having done no I/O.
3 find_want() Turns the remaining predicates into a demand mask — the fields this search will actually read.
4 scan_rec_gather() Fetches exactly that, and fills a struct llapi_scan_rec. Shared with the scanner API.
5 find_decide() Every remaining predicate, reading the record. Shared with the device scanner.

llapi_scan_namespace() uses stages 1–4 and hands the record to the caller instead of stage 5. llapi_find_device() skips 1–4 entirely — its records come off a block device — and joins at stage 5. llapi_scan_fid(), added for the changelog work below, runs stages 3–4 for a single FID resolved through a mount. Four entry points, one gather path, one set of predicates.

What a user of lfs find sees

Nothing. That is the point, and it is the part worth testing hardest. Across every sanity test that touches lfs find or lfs getdirstripe, the before and after result sets are identical — same passes, same skips, same two pre-existing failures.

Four deltas, deliberately

The directory-stripe checks now run after the stat ioctl, so a directory they reject costs one ioctl it did not before. The unstriped --foreign shortcut now prints its own object's attributes under -printf rather than the previous object's. An MDT index that cannot be fetched no longer fails the object. And a directory that is not on Lustre answers ENOTTY, which is now an answer rather than an error — so the walk descends into it instead of losing the subtree.

The record is the interface

Stage 4 produces a struct llapi_scan_rec, and that value is what makes the split work. Before it, the fetched attributes lived in a buffer owned by the search and mutated in place; there was nothing a second consumer could be handed.

Two fields let it cross a version boundary. sr_size says how much of the record the scanner filled, so a consumer built against an older definition keeps working — fields are only ever appended. sr_valid carries one bit per field, set only when the scanner could answer for it.

Why a validity mask at all

Because "could not answer" and "the answer is zero" are different things, and the old code could not express the difference. A regular file's size is the standing example: the data lives on OSTs, so the size is not the MDT's to give. Reporting 0 would be a lie; leaving LLAPI_SCAN_SIZE clear is the truth. lfs find --size then stats the file, which is why sr_parent_fd and sr_name are in the record.

The demand mask carries the answer

The mask is what lets gathering and deciding be separate functions without losing the interleaving. Stage 3 turns the search's remaining predicates into a set of fields; stage 4 fetches exactly those and no more. Without it the split would have cost every lfs find -name an ioctl per object for attributes it was about to discard.

It also encodes something the old code had no way to say: the same field is not the same cost to every scanner. A project id costs a namespace walk an open per object, and costs a scanner reading inodes off a block device nothing at all. Three fields — LLAPI_SCAN_MDT_INDEX, LLAPI_SCAN_PROJID and LLAPI_SCAN_HSM — are therefore gathered only when named, and a scan wanting nothing beyond what the directory entry knew performs no ioctl per object at all.

The per-field costs, and how to set the mask, are on the companion page.

Reading the record from your own code

The gather path this rewrite created is exposed as llapi_scan_namespace(): the same traversal and the same record, delivered to a callback instead of judged against command-line predicates. A tool that needs per-object attributes no longer has to shell out to lfs find and parse its output.

A third source: the changelog

Splitting the predicates from the gathering had a consequence nobody was aiming at. Once find_decide() takes a record rather than a directory entry, anything that can fill a record can be searched with lfs find’s vocabulary — and a Lustre Changelog can fill one. That makes a third input possible without a second copy of the predicates, which is the same argument the rewrite was made for.

Status — on Gerrit, 2026-08-29

All of it is written, lab-verified against a three-node cluster, and pushed. llapi_scan_changelog() reads an MDT’s changelog and delivers struct llapi_scan_rec, in event mode or coalesced one record per object (68415). llapi_scan_fid() fills a record for one FID the way a walk fills one (68416), which is what --since verifies each candidate with. Then --since (68417), --changelog (68418), --since-cookie (68419) and the man page and tests (68420).

Three rounds of review since have changed behaviour rather than style, and each is below: --resolve now answers -size, --since follows a file’s other names, and --changelog really does name an object whose pathname is gone — the row this page already claimed, which turned out not to work until the test for it was written.

A changelog is not a scan, and that difference decides the interface. It enumerates what happened, never what exists: an object nobody has touched does not appear, however well it matches. So there are two spellings, and they answer two different questions.

 --since--changelog
Answers as it is now as it was recorded
The changelog’s role a candidate set; every hit verified the ordinary way the whole source
The result a strict subset of an ordinary find events, coalesced to one line per object
Deletions invisible — a removed object cannot be verified visible, which is the reason this spelling exists
A predicate it cannot answer none; it verifies refused, or counted undecided

lfs find /mnt/lustre --since 2h -type f takes the FIDs of everything with an event in the last two hours, resolves each one through llapi_scan_fid(), and then applies the predicates exactly as it always has. That call is what makes the promise keepable: it fills the record the way the walk fills it — layout, HSM state, project id and all — where an fstat of its own would have answered six predicates out of eighty and left --since -stripe-count 4 disagreeing with a plain find on the same filesystem. Every flag keeps its meaning, the output is pathnames, and the answer is narrower than a full find — never different.

lfs find /mnt/lustre --changelog testfs-MDT0000 --since 4200 reads the log and nothing else. A changelog record carries a FID, a parent FID, a name, the event and its time, and — where the server recorded them — a uid and gid. It carries no size, mode, times, layout or HSM state at any setting, so those arrive absent with their sr_valid bit clear, or are filled by a lookup the caller asks for.

That lookup is --resolve, and it does two things a record cannot. It produces a pathname, which is what makes a subtree search possible at all: a changelog says nothing about where an object sits, so without it --changelog takes the filesystem rather than a directory. And handing that pathname to the decider is what answers -size — the decider stats the path, which glimpses the OSTs. Asking the MDT instead returns the lazy SOM value for a striped file, which is why -size under --resolve came back “could not be decided” for every object until the resolved path reached the decider rather than only the record.

The same question, asked of both sources

The two spellings compose — --changelog picks the source, --since picks where in it to start — so the clearest way to see the difference is to hold the query still and change only the source.

the accelerator, then the event view
lfs find /mnt/lustre --since 2h -type f
lfs find /mnt/lustre --since 2h --changelog all -type f

--changelog takes an MDT name or all, and the argument is required: getopt_long() accepts an optional argument only in the --changelog=VALUE form, and a required one accepts both spellings. So a bare --changelog followed by -type f is an error rather than a default — it would otherwise swallow -type as its value.

Given the same six things happening in the window, the two commands disagree about five of them.

In the last two hours --since 2h --since 2h --changelog all
a.log created, a regular file /mnt/lustre/a.log /mnt/lustre/a.log
b.txt appended to; created last year /mnt/lustre/b.txt undecided — the event is a write, and only a creation records the type
c.tmp created, then unlinked nothing — a removed object cannot be verified [0x200000402:0x1f:0x0]
notes.txt renamed to notes.old /mnt/lustre/notes.old, the name it has now undecided for -type; the record’s name is notes.txt, the name at the event
logs/ created, a directory nothing — not a regular file nothing — the creation recorded a directory
old.log, a regular file nobody touched nothing nothing

Two rows carry the whole trade. c.tmp is the one only --changelog can answer — there is no object left to verify, so the FID is the answer or there is none. old.log is what both spellings cost: it matches -type f perfectly and neither prints it, because it has no event. Everything between those two rows is the same distinction read twice: --since asks which files are like this now, among those that changed; --changelog asks what the log says happened.

One more thing is the same in both: 2h is the time spelling, and under DNE it is the only one that means the same thing on every MDT. A bare --since 4200 is an index into one MDT’s log, so on a multi-MDT filesystem it is refused as ambiguous unless a single --changelog MDT names which log it indexes.

--since-cookie is the exact form of the same thing. It holds one anchor per MDT in a file and rewrites each with the index that MDT reached, so a repeated job resumes where it stopped on every log rather than at a time the logs only approximate. It also refuses: if an MDT has purged past its anchor the records in between are gone, and returning what is left would be a short answer with nothing to say so. Every anchor is checked before any MDT is scanned, so that refusal cannot arrive after part of the answer is already on stdout.

Four ways a flag gets refused

It needs object state and --resolve was not given; it describes a walk (--maxdepth); it needs the mounted filesystem’s target list (--ost); or the record carries something that is not what the option means — which is why -name is answered from the event and --mdt is refused outright. A predicate is answered from what the source actually has, or refused. It is never approximated, and never reinterpreted.

That rule is also why a flag may mean different things on different commands without it being a defect: lfind --name already matches every linkea name where lfs find --name matches the name the walk arrived by. The promise worth keeping is not that flags behave identically everywhere, but that an answer is never invented.

--since sits between those two, and getting it wrong was silent. There is no walk to have arrived by, so a FID resolves to linkno 0 — the name the file was created under. A search rooted at a directory holding the file’s other link therefore dropped it, and -name was answered about one basename where the file goes by two. Both now walk every link a file with more than one has, which is what keeps --since a subset of the search it claims to be a subset of, rather than merely a smaller answer.
