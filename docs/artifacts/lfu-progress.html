Where it stands

The work is split in two, and the split is by where the code runs rather than by feature:

 What it isRelease
Phase 1 Userspace design and implementation — the client-side namespace scanner, the device scanner and its backends, the changelog scanner, and lfs find and lfind on top of them. Nothing here needs a kernel change. Lustre 2.18
Phase 2 In-kernel design and implementation — the OSD API scanner running inside the server, the circ_buf ring that carries its output to userspace, and the bulk RPC modules that carry a stream between nodes. Lustre 2.19

The division is Dilger’s, set on 2026-08-19; the phase numbering is ours. It matters mostly because 2.18 is a deadline rather than a sequence — which argues for landing Phase 1 pieces one at a time rather than holding them for a complete series.

The number that matters is the last one. Everything below is written, built, lab-verified and posted for review; nothing has been merged. Fifteen of the nineteen changes are LFU feature work, and four are pre-existing upstream defects found while building on the code and fixed separately rather than folded in.

The four bugs are worth counting as output

LU-20624 (a stale descriptor in cb_get_dirstripe), LU-20643 (lfs find answering -btime from a reused buffer), LU-20647 (a plainly registered changelog user could not be looked up at all) and LU-20648 (--mask silently dropped for a user who has none). None was introduced by this work. Three of the four were found by reading the code the scanner was being built on; the fourth by the first lab run of the changelog module.

Two more have been found since and are not filed: a 284-byte overrun in convert_lmdbuf_v1v2(), reachable when the *_V2 ioctls answer ENOTTY, and a byte-swap gap in layout_swab_lov_user_md() that leaves a foreign layout in the target's byte order on a big-endian client. Both were verified by compiling a probe rather than by reading. Each wants its own ticket.

Where the time is going now

Seventeen rounds of review fixes, every one of the nineteen changes at patch set 3 or later and the most-revised now at 16 — and the reviews, and writing the tests they ask for, are still finding defects rather than style. Two on 2026-08-29; fifty-seven more in the three rounds since, from 183 review comments. Round 17 alone answered 63 comments and fixed 18 defects, and every one of the nineteen changes now holds jenkins Verified+1.

The --since-cookie parser bounded an MDT index as a signed value while indexing the anchor array with an unsigned one, so a cookie line reading <fsname>-MDT-1 parsed to 0xffffffff and stored 32 GiB past the end. The sanity case added with the fix segfaults against a build with the old test put back.

And stating the POSIX scanner's contract — which fields a record carries when a stat is the source — found that every file scanned outside Lustre came back with a FID built from its own filename, with the validity bit set to say it was real. Neither defect was found by reading the code. Both were found by writing down what it was supposed to promise. That is an argument for landing in pieces, not against it.

Round 17's largest finding was not in the review at all. The AI said three times that a claim in lfind --fid2path's documentation was false — that a FID from another filesystem could not resolve against the wrong mount. It can: sequences are not unique across filesystems. Guarding it exposed something bigger, and the lab, not the review, found it: see below.

The clearest of the twenty-four found on 2026-08-31 has the same shape. lfs find has no --hash-type and no --hash-flag — -H/--mdt-hash is what sets those fields. Yet the man page listed them, the refusal message named them back to the user, and the new test exercising the refusal exited non-zero from getopt rather than from the refusal, so it would have kept passing if the option were deleted outright. Three artefacts agreed with each other and none with the code.

The performance target, and the condition on it

The HLD asks for 1M objects/s per MDT, assuming at least 1 GiB/s read on the MDT device, exclusive of pathname generation. Measured on 2026-08-16 against exactly that, on a 1,406 MB/s NVMe stripe with 20M objects:

 Rate4×109 objects
The userspace device scanner1,435,080 obj/s0.78 h

That is 93% of the raw device, from a single thread, because ext2fs_inode_scan reads a block group's inode table in long sequential runs.

The condition is the part to carry forward

93% of the device means the scanner effectively has the device. That holds for an unmounted target, a snapshot, or a failover partner's LUN. On a serving MDT the scan shares bandwidth with the MDT's own I/O and gets proportionally less; on a snapshot it pays copy-on-write indirection on top. Phase 2 does not fix this — the in-kernel scanner reaches 99% of the same device, and the device is the ceiling either way.

Built beyond what the HLD asked for

Three pieces exist that the HLD does not name, each because building the named ones made the gap obvious.

 WhyWhere
lfind(8)the HLD names a device scanner but no command to drive it68160
ZFS backend for the device scannerthe HLD's device scanner is ldiskfs only; a ZFS site would have had nothing68163 — LU-20613
lfs find --since, --changelog, --since-cookiethe Changelog Input Scanner has no user without them68416–68420 — LU-20650

The last of those is the one worth explaining. A changelog answers what happened, never what exists, so it reaches a user two ways: --since treats the log as a candidate set and verifies each hit against the live object, and --changelog reads the log and nothing else. The first answers as it is now, the second as it was recorded — which is why an object deleted during the window appears under one and cannot under the other.

Naming a target's objects without asking that target

Added 2026-09-01, in 68288 and not yet pushed. Until now lfind --device … --fid2path resolved every object by its own FID, which routes to the target holding it — an OST object through the OSC, an MDT object through the MDC. But a scan reads a target that is out of service, and on ZFS it must be: the backend refuses an imported pool, at pool granularity, so scanning a snapshot does not help either. The two requirements could not both hold, and the failure was an indefinite hang rather than an error.

TargetHow the path is found nowVerified
OST the owning file's FID from the object's own trusted.fid, resolved against the MDT ldiskfs 12/12 and conf-sanity 167; ZFS 10/10 with the pool exported
MDT the object's trusted.link plus a map of the target's directories, built by a pass before the search ldiskfs 9/9 offline, equal to the mounted answer; ZFS 10/10 with the pool exported
Two things are counted rather than named

An OST object no file owns yet — precreated and never written, of which a target holds many — carries no trusted.fid and has no name. And on DNE the directory map covers only the target scanned, so an object whose ancestors live on another MDT cannot be placed. Both are reported in the closing count rather than guessed at.

Every defect in this change was found by a lab and not by review: a label parser that read one of the four separators mkfs.lustre writes; a fallback that reached for the very lookup the change exists to avoid, on the objects a scan meets first; and a demand mask that never asked for the linkea the walk depends on. The test that found them compares the set of names against what the client saw before the target went down — a scan that resolves nothing and one that resolves everything both exit 0.

Also open on the epic and untouched: LU-20602, MDT-internal objects carrying no LMA flag to mark them internal — which is why a target scan cannot cleanly tell a user's object from the filesystem's own.

Phase 2, deliberately untouched

Phase 2 is the in-kernel half, for 2.19: the OSD API Input Scanner, the circ_buf kernel→userspace ring, and the bulk RPC modules on both sides. None of it is submitted, and that is the plan rather than a slip.

Two things about it are already known rather than assumed. The OSD scanner has been prototyped and measured — 2.03M obj/s on ldiskfs with private per-shard iterators, against 705k for the userspace scanner on the same warm cache. And the ring has a working precedent in tree: lustre/ofd/ofd_access_log.c already exports the OST access log kernel→userspace with exactly the circ_buf plus .read plus .poll structure the HLD asks for, so it is a pattern to copy rather than invent.

One phrase in the epic needs qualifying

The epic lists "zero-copy lockless ring-buffer kernel→userspace export". Lockless, yes. Zero-copy is aspirational as written: the in-tree precedent uses .read, which copies once from the ring into the user buffer. Genuine zero-copy needs .mmap of the ring pages with head and tail in a shared control page — more work and more attack surface, and worth measuring against the read() path before committing to it. The requirements rank zero-copy export only Medium, below the scanner itself.

What could go wrong

RiskShape of it
Nothing has landed Nineteen changes in review is the largest the series has been, and 2.18 is a deadline rather than a sequence. The argument for landing pieces one at a time gets stronger, not weaker, as the stack grows.
The format decision is external Three of the four remaining Phase 1 items sit behind it, and its evaluation has not started. Nothing we do moves it.
DNE is not covered Without Merge/Split, a device scan is per-target. Anyone testing lfind on a multi-MDT filesystem will find that out quickly, and it will read as a defect rather than as a module that is not written yet.
The new sanity cases are young Largely resolved. All seven sanity cases (157c, 160y, 160z, 160aa–160ad) run PASS twice over with SKIP 0 on the two-MDT lab, as do conf-sanity 165, 166 and the new 167, and every one of the nineteen changes holds jenkins Verified+1 on its current patch set. The framework keeps earning it: it caught 160ac assuming a stale cookie rather than making one, and 160ac's two refusal cases passing on that stale anchor instead of on the refusal they name. What is still young is the enforced autotest sweep against the round-17 patch sets, which is in flight.
