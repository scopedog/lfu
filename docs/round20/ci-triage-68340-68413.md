# The two unaccounted CI failures — neither is ours

Triaged 2026-09-03. Both were the only enforced failures on our board not
already attributed to a known class.

## Where the subtest names came from

Gerrit's Maloo message names only the **suite** (*"1 tests failed:
recovery-small"*), which is the same wording a real assertion failure and a
session timeout both produce. The session pages at
`testing.whamcloud.com/test_sessions/...` need a login we do not have.

**The Janitor's own Gerrit comment names the subtests, and it is public.**
`lgerritjanitor` posts a "Testing has completed with errors!" message listing
each failing suite with its subtest and the assertion text in parentheses. Use
that instead of trying to read Maloo, and instead of a `WebFetch` summary of a
results page — which cannot tell "absent because it passed" from "absent
because it never ran", the mistake that cost a wrong conclusion on `test_167`.

## 1. 68340 PS3 — `recovery-small`

Janitor job 69077: `recovery-small@ldiskfs+DNE Failure(6971s)` —
**`24b(no discarded dirty page found!)`**.

**Already a known class.** The noise table has `recovery-small` 24b: *"ends in
`dmesg | grep "dirty page discard:"` after `dmesg -c`; loses the race when the
ring rolls."* The test evicts a client, then greps the kernel ring buffer for
one message; over a 6971-second run the ring can roll before the grep.

**And mechanically out of reach.** 68340 changes exactly one file,
`lustre/utils/liblustreapi_pfind.c` — 18 lines of userspace, clearing a reused
`lov_user_mds_data` for `lfs find`. `recovery-small.sh` calls `lfs find`
**zero** times, and `test_24b` is `multiop` + `ost_evict_client` + a `dmesg`
grep. There is no path from the change to the failure.

## 2. 68413 PS6 — `sanityn`

**Not covered by the existing entry.** The noise table's
`review-dne-part-5`/`sanityn` line was written for 68095 and 68340, both
*userspace* changes, and its argument is that userspace cannot reach a
two-client suite. 68413 is **server-side MDD**, so that argument does not
transfer and had to be redone.

68413 changes `mdd_changelog_user_lookup_cb()` in `lustre/mdd/mdd_changelog.c`
(plus tests in `sanity.sh`). Its only call site is

    lustre/mdd/mdd_device.c:2322
      case OBD_IOC_CHANGELOG_FILTER:
        rc = mdd_changelog_user_lookup(env, mdd, karg, karg);

an **ioctl**, not a mount, recovery or teardown path. `sanityn.sh` mentions
`changelog` **zero** times, so it never issues that ioctl and the changed
function is never entered during the suite. Out of reach.

The prior holds too: the same session-and-suite has been hit by seven other
owners since 2026-08-19 out of 159 changes with a Maloo run, and on our series
it timed out in `test_cleanup` — teardown, not an assertion.

### The Janitor's "unique to this patch" flag, checked

68413's Janitor message carries a header we have not seen before:

    IMPORTANT: these tests appear to be new failures unique to this patch
    - sanity-quota@zfs:test_48(Seen in reviews: 65510 64320)

**The header is contradicted by its own parenthetical**: two unrelated reviews
have the same failure. `sanity-quota.sh` mentions `changelog` zero times, and
test_48 is *"lfs quota --delete should delete quota project ID"* — quota
project IDs, nowhere near changelog user lookup. Same discriminator that
settled `sanity-sec`: when changes sharing nothing fail identically, the
failure is the tree's.

## Everything else in those two jobs

Already-classified noise, listed so the next sweep does not re-derive it:
`racer@ldiskfs+DNE` timeout (both), `sanity-pcc` 1c/1d on both backends
(LU-524/526), `recovery-small@zfs` 155 (LU-401), `pjdfstest@zfs` timeout,

## Outcome

**No fix required for either.** Neither change can reach its failing suite,
by call-graph rather than by inference from absence.
