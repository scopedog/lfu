## 68616 — `LU-4315 contrib: let SEE ALSO carry subsections`

**(1) The commit message's "39 warnings" was attached to the wrong thing.**
Measured with the pre-patch script on the `.SS`-grouped page:

    perl uninitialized-value warnings   39   (13 x $prevfile + 26 x $prevnum)
    SEE ALSO style/comma warnings       28
    checkpatch warnings, total          42

So 39 is the *perl* count, and the message had it in the paragraph about
malformed-reference reports, which are 28. The second claim — *"a pair of
uninitialized-value warnings from perl for every reference in the page"* —
was wrong too: it is **three on the first reference of each of the 13
subsections**, not two per reference, of which the page has 141 (that would
be 282). Message corrected on both counts.

**(2) The `.PP` now ends the preamble.**
`$see_also_preamble` was only cleared when a reference was seen, so any
number of description lines and `.PP` lines were accepted in any order until
the first reference — prose after the `.PP` went unreported where it used to
be caught. The comment above the flag already described the stricter rule.

    -    next if ($see_also_preamble &&
    -             ($line =~ /^\.PP$/ || $line !~ /^\./));
    +    if ($see_also_preamble && $line =~ /^\.PP$/) {
    +            $see_also_preamble = 0;
    +            next;
    +    }
    +    next if ($see_also_preamble && $line !~ /^\./);

Verified with a page crafted to discriminate — `.SS`, description, `.PP`,
then stray prose, then references. Before: accepted silently. After:
reported. **And swept all 378 pages with that change alone: not one count
moved**, so nothing in the tree trips the tightened rule.

**(3) The `Fixes:` tag the reviewer asked for**, confirmed to be the commit
that introduced the script (958 lines of it):

    Fixes: d15955d374d5 ("LU-4315 doc: add man pages to checkpatch")

**(4) The consequence of widening `$llapi`, now stated.** It also selects the

Confirmed by running the new script against the page as of this commit.

## 68340 — the lreview finding

`liblustreapi_pfind.c:295`. The comment on the new `memset` said the region
it clears holds *"the previous conversion's bytes"*. It does not, on this
path: `offsetof(v1, lmd_lmm)` is 144 and `offsetof(v2, lmd_lmm)` is 288, and
the `memmove` immediately above copies the LOV EA up from 144 — so what is
left at 144..288 is **the head of this object's own V1 LOV EA**, and only
past the EA's own length is it the previous call's. The `memset` is right
either way; the reason given was not. Comment and commit message both fixed.

### Noted, not fixed: the memmove length is upstream and looks wrong

    memmove(&lmd_v2->lmd_lmm, &lmd_v1->lmd_lmm,
            lmdlen - (&lmd_v2->lmd_lmm - &lmd_v1->lmd_lmm));

Both operands of the subtraction are `struct lov_user_md_v1 *`, so the
difference is in **elements, not bytes** — 144 bytes over a 32-byte struct,
which truncates to 4 rather than 144. The length would then be `lmdlen - 4`
where `lmdlen - 144` was meant, reading past the buffer.

`git log -S` puts the line in `48a82603b8 ("LU-19052 utils: move find code
into liblustreapi_pfind.c")`, a **move** commit — so it is upstream and
predates us. Not fixed here, and worth its own ticket rather than folding
into a change about something else.
