# 68288 and 68416's AI reviews — five fixed, one disproved by measurement

## `8d405103` on 68288 — marked *(defect)*, and it is a false positive

The claim: `--paths` is refused by testing whether the directory pass
found anything (`st.fds_dirmap.dm_used == 0`), which is not the same as
"this is an OST" — so **an MDT whose files all sit directly in the
filesystem root would build an empty map and be refused with a message
about an OST**, even though every file would compose to `/<name>`.

Reasonable on its face. So I built exactly that filesystem: a fresh
single-MDT mount, three files in the root, no directories at all,
unmounted, and scanned the image.

    # lfind --device /tmp/lustre-mdt1 --paths --type f
    lfind: 2 matching objects have no pathname and were not printed
    /a
    /b
    /c

**It works.** The premise is wrong: a real MDT is never without
directories. That "flat-root" MDT has **116** of them — `ROOT`, `O/`,
`REMOTE_PARENT_DIR` and the rest of the OSD's own tree — so `dm_used` is
never 0 on an MDT, and the empty-map case the finding depends on does
not arise.

And the refusal still fires where it should:

    # lfind --device /tmp/lustre-ost1 --paths --type f
    lfind: --paths composes a pathname from an MDT's own directories,
           and '/tmp/lustre-ost1' has none; ...
    exit 1

Its secondary observation stands and is **recorded, not fixed**: the
directory pass runs unconditionally for both `--fid2path` and `--paths`,
including on an OST where it reads one object and throws the map away,
and on ZFS a second open costs `spa_export()` plus `kernel_fini()`.
`tt_flags` already carries `LLAPI_SCAN_TGT_MDT`/`_OST` at open time, so
handing it back out of the scan would skip that pass. That is a
worthwhile optimisation across the scan API boundary, not a correctness
fix, and it belongs with the other API work rather than tonight.

## The finding that my own test proved — `09d04fc1`

`lfind.8` told the reader that an object whose ancestors live on another
MDT can be resolved by taking "the FIDs it printed" to
`lfs-fid2path(1)`. The run above answers that directly:

    lfind: 2 matching objects have no pathname and were not printed

They are **counted, not printed** — and under `--paths` or `--fid2path`
the FID-printing arm is never taken at all, because those options are
what replace it. The advice pointed at output that does not exist.

Now says what actually works: scan those MDTs too, or run the same
search *without* either option to get the FIDs.

## `43c55067` — a font bug, and the suggested fix was the wrong mechanism

`.IR` alternates italic and roman, so in

    .IR MOUNT " | " \-\-paths ]

`--paths` landed in **italic** — the value font — where `--internal` and
`--fid2path` are bold. Real, on all four SYNOPSIS lines.

The comment proposed `\fB\-\-paths\fR`. That renders correctly but
**`checkpatch-man.pl` forbids it** — "Avoid using \\f[BIR] for
formatting purposes" — and applying it took the page from 1 warning to
5. Used the macro form instead:

    .I MOUNT
    .RB "| " \-\-paths ]

which renders `[--fid2path MOUNT | --paths]` with `--paths` bold and the
spacing right, and leaves the page at its 1 pre-existing warning. Worth
noting because the suggestion was right about the bug and wrong about
the remedy, and only rendering both told them apart.
